# 02 · 架构设计与集成契约

> 角色：架构师。本文只定义边界、契约、语义与迁移顺序，不写实现代码。
> 快照：2026-11-14 23:07 CET；迁移：2026-11-14 23:52 CET。目标不是“再做一个工具”，而是让现有三个工具**成为一套系统**，并堵住官方 R1。
> 迁移提示：`app/`、`数据库工具/`、`视图工具/`、`docs/`、`tools/`、`参考 资料/` 已移入 `系统/`；本文路径为设计时点。

---

## 1. 设计原则（可用来否决任何提案）

1. **单一事实源**：目标/历元/帧/覆盖只维护一份；其他工具只读或使用**可校验的物化视图**。
2. **契约优先于复制**：任何跨工具数据都必须有 schema、版本、黄金样本和对账命令；“复制一份 JSON”只能作为离线缓存，不能成为第二事实源。
3. **诚实降级**：真实数据不可用时，必须显式标 `REAL / HYBRID / SIM / UNAVAILABLE` 和原因；不允许把“取数失败”写成“基线不足”，不允许把模拟结果说成观测结果。
4. **覆盖 ≠ 检测**：目录能回答“拍没拍过”，只有测量管线能回答“测没测到”。两者不得共用同一个 `readiness`。
5. **离线可演示**：演示路径不依赖 IRSA；网络是增强，不是前提。
6. **单一入口**：用户只面对 MoveScope；数据库和视图工具是支撑，不是并列产品。
7. **可回滚**：每次数据/契约变更都要有快照、版本号和回滚路径。

**结构性问题：**

| 问题 | 表现 | 后果 |
|---|---|---|
| 星形复制，不是分层 | targets 3 份、历元 2 套、fields 2 份 | 漂移（coord_unc 缺失、RW truth 为 null） |
| 数据层无人消费 | app 不调 DB；view 不调 DB | DB 是 shelfware；R1 无法闭环 |
| 两套 HTTP API | app `/api/epochs`、DB `/api/epochs` 形状不同 | 嵌入方/前端无法互换 |
| 两套“就绪度” | DB 曝光覆盖 vs app 检测质量 | WISE 0855 DB L2 / app L0 |
| 三套覆盖阈值 | 1.745 / 1.9 / 7.5 / 2.47 | 同一目标不同工具结论矛盾 |
| 无控制面 | 无验收、无快照、无启动器 | 演示靠人肉，回归靠记忆 |

## 3. 目标架构（to-be）：四平面

```
┌─────────────────────────────────────────────────────────────────────┐
│ L4 控制面   项目主控/                                                │
│   契约 schema · 验收 harness · 快照/漂移检查 · 启动器 · 演示冻结      │
└───────────────┬─────────────────────────────────────────────────────┘
                │ 只读检查 / 启动 / 冻结
┌───────────────▼─────────────────────────────────────────────────────┐
│ L3 体验面                                                            │
│   MoveScope Web（唯一入口，:8790）                                    │
│   └─ 可选：视图工具（天区上下文，:8830）──深链（target_id + 全精度）──►│
└───────────────┬─────────────────────────────────────────────────────┘
                │ Analysis API（一次请求/结果）
┌───────────────▼─────────────────────────────────────────────────────┐
│ L2 计算面   MoveScope core                                           │
│   取切片 → FLAGS 掩膜 → 测光/质心 → 相对定标 → 关联 → BIC → 判定      │
│   拥有：分析结果、质量标记、analysis_readiness、公众话术、证伪条件     │
└───────────────┬─────────────────────────────────────────────────────┘
                │ Epoch Query（v1 契约，只读）
┌───────────────▼─────────────────────────────────────────────────────┐
│ L1 数据面   数据库工具                                                │
│   SQLite catalog + Blob store + 采集/导入/导出 + coverage/cone        │
│   拥有：targets、frames、target_epochs、cutouts、blobs、provenance    │
└───────────────┬─────────────────────────────────────────────────────┘
                │ 采集（S3 Range / 静态切片）
┌───────────────▼─────────────────────────────────────────────────────┐
│ L0 数据源   IRSA 静态切片 · S3 公开桶 · SIMBAD（参考）                 │
└─────────────────────────────────────────────────────────────────────┘
```

**关键点：**

- **L4 是新增的，但不是新产品**：它是 `项目主控/` 里的脚本/文档/检查，不对外服务。
- **L1 是唯一数据源**：MoveScope 不再“自己维护 epoch_catalog.json 作为事实源”；本地 JSON 只是 L1 的导出缓存。
- **L2 是唯一测量者**：数据库不参与测光/分类；视图工具不参与测量。
- **L3 只有一个产品入口**：视图工具是可选伴侣，不是并列入口；如果修不好，就从演示路径移除。

## 4. 数据所有权（RACI 简化）

| 数据/能力 | Owner | 只读消费方 | 禁止 |
|---|---|---|---|
| 目标坐标、truth、`coord_unc_arcsec` | 数据库 `targets` | app（导出或 API）、view（API） | app/view 各自维护副本 |
| 观测帧/曝光/周/处理版本 | 数据库 `frames/observations/weeks` | app、view、验收 | app 从 fields.json 反推事实 |
| 目标候选历元 | 数据库 `target_epochs` | app、view | app 手写 epoch_catalog 作为唯一源 |
| 切片缓存（NPZ/FITS） | 数据库 Blob（索引）+ app 本地缓存（像素） | app | 两套互不相认的缓存 |
| 覆盖/可用性 | 数据库 `coverage` | app、view、验收 | 用检测质量口径冒充覆盖 |
| 测光、轨迹、BIC、判定 | app `pipeline/motion` | 数据库（只存结果摘要，可选） | 数据库做科学判定 |
| 分析就绪度 L0–L3 | app | UI、验收 | 数据库直接给 app 的 readiness 赋值 |
| 契约 schema/黄金样本 | 项目主控 | 三工具 | 任一工具私自改字段 |
| 启动/端口/快照 | 项目主控 | 三工具 | 各自扫端口、各自起服务 |

**一句话：数据库管“有没有、在哪、什么时候”，app 管“动没动、为什么”，项目主控管“算不算过”。**

## 5. 契约 v1

### 5.1 规范 DTO

#### `Target`（7 条，字段必须齐全）

```json
{
  "id": "barnard",
  "name": "Barnard's Star",
  "name_zh": "巴纳德星",
  "official": true,
  "ra": 269.452077,
  "dec": 4.693365,
  "type": "M4V",
  "expected": "L",
  "coord_unc_arcsec": 3.0,
  "truth": { "mu_mas_yr": 10393.4, "pa_deg": 355.6, "parallax_mas": 546.98,
             "pmra_mas_yr": -801.551, "pmdec_mas_yr": 10362.394,
             "period_d": null, "amp_mag": null },
  "note": "..."
}
```

规则：
- `coord_unc_arcsec` 必填（缺失按 0 处理是错误，不是默认）。
- `truth` 只用于验收对照，不参与拟合；导出到公开 API 时默认剔除（`?include_truth=0`）。
- app、数据库、视图三处必须逐字段一致；`tools/check_compat.py` 已能对账。

#### `EpochRef`（历元引用，两个 API 必须同形）

```json
{
  "obsid": "2025W35_2A_0221_1",
  "detector": 2,
  "release": "dr1",
  "week": "2025W35_2A",
  "version": "l2b-v27-2026-231",
  "mjd": 60916.656062,
  "date_obs": "2025-08-29T15:44:43.747",
  "sep_deg": 0.229,
  "key": "dr1/level2/2025W35_2A/l2b-v27-2026-231/2/level2_2025W35_2A_0221_1D2_spx_l2b-v27-2026-231.fits",
  "slice_url": "https://irsa.ipac.caltech.edu/ibe/data/spherex/...?center=269.452077,4.693365d&size=0.25",
  "provenance": "real",
  "frame_id": 744
}
```

规则：
- 十字段必填：`obsid / detector / release / week / version / mjd / date_obs / sep_deg / key / slice_url`。
- `date_obs` 不得为 null；缺失时由 `mjd` 反推 UTC ISO 字符串。
- 同一 `(obsid, detector)` 只出现一次；同一 `mjd`（±0.02 d）按“离查询点最近”去重。
- 排序：先 `mjd` 升序，再 `detector` 升序；分页稳定。
- `slice_url` 的 `size` 必须等于查询 `fov`；不要固定 0.05 或 0.2。
- `provenance` 只能是 `real | hybrid | synthetic | unknown`；来自目录的真实历元一律 `real`。

#### `Coverage`（只描述“观测机会”，不描述“检测质量”）

```json
{
  "ra": 269.452077,
  "dec": 4.693365,
  "radius_deg": 2.47,
  "n_frames": 10,
  "n_epochs": 4,
  "n_observations": 4,
  "n_weeks": 3,
  "baseline_days": 203.62,
  "mjd_min": 60916.65,
  "mjd_max": 61120.28,
  "detectors": [1, 2, 4, 5],
  "releases": ["dr1"],
  "coverage_level": "C2",
  "header_available": false,
  "n_local_cutouts": 3
}
```

- `coverage_level` 用 **C0–C3**，不要复用 app 的 L0–L3，避免语义碰撞。
- `radius_deg` 默认 **2.47°**（单片半对角线）；若用 1.745° 必须在响应里显式写出，不允许“默认保守但不说”。
- `header_available` 表示该天区是否有 FITS 头；没有头时 `date_obs`、`pixel_scale` 等可能缺失，调用方必须知道。

#### `AnalysisResult`（app 现有结构 + 三个必填字段）

```json
{
  "schema_version": "1.0",
  "data": {
    "mode": "real",
    "provenance": ["real"],
    "fallback_reason": null,
    "n_epochs": 8,
    "note": "..."
  },
  "result": {
    "class": "L",
    "readiness": "L3",
    "readiness_scope": "analysis",
    "quality": ["LARGE_CENTROID_ERROR"],
    "fingerprint": { "...": "..." },
    "evidence": ["..."],
    "falsifier": "..."
  }
}
```

`fallback_reason` 枚举：

| 值 | 含义 | 允许的 `mode` |
|---|---|---|
| `null` | 没有降级 | real / hybrid / sim（用户主动选） |
| `NO_LOCAL_COVERAGE` | 本地目录没有该天区 | synthetic |
| `INSUFFICIENT_EPOCHS` | 有历元但 <2 期 | hybrid / synthetic |
| `BASELINE_TOO_SHORT` | 历元 ≥2 但基线 <30 天 | hybrid |
| `FETCH_FAILED` | 有历元但切片取不回来 | **UNAVAILABLE**（不建议静默 SIM） |
| `TARGET_TOO_FAINT` | 有历元但 <2 期达 3σ | real（L0/U） |

规则：
- `mode` 与 `provenance` 必须自洽：`real` 不能包含 synthetic epoch；`hybrid` 必须至少有一个 real 组件（背景/PSF）并显式说明。
- `FETCH_FAILED` 不得伪装成 `BASELINE_TOO_SHORT`；UI 应显示“取数失败，请重试/离线缓存”。
- `quality` 是**累加**，不是覆盖：管线各阶段只能 append，不能整体替换。

### 5.2 API 契约

#### `GET /api/v1/epochs`

参数：
- `target_id=<id>` 或 `ra=<deg>&dec=<deg>`（二选一；同时给时以 `target_id` 为准并校验坐标一致性）。
- `fov=<deg>`（0.02–3.5，默认 0.25）。
- `radius=<deg>`（默认 2.47，允许 0.2–5）。
- `release=dr1|qr3`（可选）。
- `limit/offset`（默认 500/0，最大 2000）。
- `format=movescope`（兼容旧形状；默认 `v1`）。

响应：

```json
{
  "schema_version": "1.0",
  "query": { "target_id": "barnard", "ra": 269.452077, "dec": 4.693365,
             "fov": 0.25, "radius": 2.47, "release": null },
  "coverage": { "n_epochs": 4, "baseline_days": 203.62, "coverage_level": "C2" },
  "epochs": [ { "...": "EpochRef" } ],
  "count": 4,
  "generated_at": "2026-11-14T22:07:00Z"
}
```

**验收硬规则：**

1. `target_id=barnard` 与 `ra=269.452077&dec=4.693365` 必须返回**同一组 EpochRef**（4 条去重后）。
2. 同一条历元的 `obsid/key/date_obs/sep_deg` 必须逐字段一致。
3. `?target_id=rw_aur` 与 `?ra=76.956526&dec=30.401438` 都必须返回 1 条真实历元（不是 0）。
4. 不允许 `date_obs: null`；不允许 `key` 缺失；不允许同一 `(obsid,detector)` 重复。
5. 无效 FOV/RA/Dec 返回 400，不是 500。

#### `GET /api/v1/coverage`

返回 `Coverage`，并额外给 `n_local_cutouts`、`header_available`。**不返回** `readiness`/`L0–L3`。

#### `GET /api/v1/analyze`（app 内部，不必跨进程）

保持 POST `/api/analyze`，只补 `schema_version`、`data.provenance`、`data.fallback_reason`、`result.readiness_scope`。

#### `GET /api/v1/health`

三服务统一字段：

```json
{
  "ok": true,
  "service": "movescope|spherex-db|skyview",
  "version": "0.2.0",
  "schema_version": "1.0",
  "data_snapshot": "2026-11-14T22:04:19Z",
  "counts": { "targets": 7, "frames": 5857, "epochs": 74 }
}
```

规则：`GET` 必须可用，**不要只实现 POST/HEAD**；视图工具的探测应改用 GET，或 app 补 `do_HEAD`。

## 6. 就绪度：拆成两个概念

| 概念 | 回答 | Owner | 取值 | UI |
|---|---|---|---|---|
| `coverage_level` | 这块天**拍过几次、跨多久** | 数据库 | C0（≤1）/ C1（2）/ C2（3–5）/ C3（≥6 且 ≥180 d） | 只在“覆盖”提示里用 |
| `analysis_readiness` | 这个**目标测到几期、够不够判** | app | L0（≤1 探测）/ L1（2）/ L2（3–5）/ L3（≥6 且 ≥0.6 yr） | 鉴定卡主徽章 |

**为什么必须拆：**

- WISE 0855：数据库覆盖 C2（5 期、0.95 天），但 app 只探测到 1 期 → L0/U。若共用，会把“不可判定”显示成“L2 可测速率”。
- Barnard：数据库 1.745° 覆盖 C2（3 期、6.45 天），app 用 2.47° 的 4 期、204 天 → L2。数值相同，含义完全不同。
- RW Aur：数据库 1.745° C0，但目录里有 1 条真实历元；2.47° 下 C2（6 期、0.95 天），仍不足以测运动。单看 C 级会误导。

**UI 文案：**

- `coverage_level`：显示为“本地覆盖 C2 · 4 期候选”，灰色小字。
- `analysis_readiness`：显示为“L3 就绪度”，主徽章。
- 两者不一致时，必须解释：“覆盖到 5 期，但只有 1 期达到 3σ，因此 L0。”

## 7. 降级与失败矩阵

| 场景 | 数据层 | 计算层 | UI | 允许的结论 |
|---|---|---|---|---|
| 正常，本地有头+切片 | 返回 4 条 real | 取缓存/IRSA | REAL | L0–L3 |
| 本地有历元，无切片，网络可用 | 返回 real 历元 | 取 IRSA | REAL | L0–L3 |
| 本地有历元，网络失败 | 返回 real 历元 | 标 `FETCH_FAILED` | **UNAVAILABLE**（可重试） | 不判定 |
| 本地无该天区 | `count=0`，`coverage_level=C0` | 标 `NO_LOCAL_COVERAGE` | SIM（明确“演示”） | U/S 仅演示 |
| 有 1 期 | C1 | 标 `INSUFFICIENT_EPOCHS` | HYBRID/SIM | L0/U |
| 有 ≥2 期但 <30 天 | C2 | 标 `BASELINE_TOO_SHORT` | HYBRID | L0/L1 |
| 目标饱和 | real | `SATURATED_SOURCE` | REAL + 警告 | S + 上限 |
| 目标太暗，<2 期 3σ | real | `FEW_EPOCHS` | REAL + 警告 | U/L0 |
| 数据库不可用 | — | 回退到本地导出 JSON | REAL（缓存） | 不阻断 |

**硬规则：**

- `fetch 失败` ≠ `baseline 不足` ≠ `没有覆盖`；三者必须三个 `fallback_reason`。
- 任何 SIM 结果都必须有 `note` 解释“为什么不是真实数据”。
- `quality` 只能累加；UI 必须渲染全部。

## 9. 迁移顺序（不破坏现有可运行状态）

### 阶段 0：冻结基线（0.5 天）

1. `git init` + 首次提交 + tag `baseline-2026-11-14`。
2. 保存 `项目主控/evidence/2026-11-14_snapshot.json`。
3. 三工具源码在验收前不再并行改动；改动走分支/PR。

### 阶段 1：导出契约先过关（0.5 天）

1. 保持 app 读本地 JSON，不改运行方式。
2. 数据库 `export all` → `check_compat.py` 必须四项 OK。
3. 把 `check_compat.py` 纳入验收工具，作为“数据层更新”的门禁。
4. 这一步已经可用：当前 5,857/74/7/151 全部通过。

### 阶段 2：R1 接线（1–2 天）

1. 数据库补 `?ra=&dec=&fov` 的规范 DTO（`key/obsid/date_obs` 齐全、去重、`date_obs` 非空）。
2. 覆盖半径默认改 2.47°（或按 footprint + 422 探测），并在响应里报告 `sep_deg`。
3. app 的 custom 分支：
   - 先查数据库 `/api/v1/epochs?ra&dec&fov`；
   - 有 ≥2 条 → 走真实取数；
   - 0 条 → `NO_LOCAL_COVERAGE`，显示 SIM 并明确标注；
   - 取数失败 → `FETCH_FAILED`，不伪装成“基线不足”。
4. 验收：
   - 手动输入 Barnard 精确坐标 → REAL 4 期、L2、S（与预设一致）；
   - RW Aur → 1 条真实历元（不是 0）；
   - WISE → REAL 8 期、L0/U（与预设一致）；
   - 未覆盖天区 → 明确 SIM + 原因。

### 阶段 3：视图工具交接（0.5–1 天）

1. 读 `?ra=&dec=&fov=&target=`（search），保留 hash 兼容。
2. 跳转 `${MOVESCOPE_ORIGIN}/?target=<id>&ra=<full>&dec=<full>&fov=<fov>`，坐标用全精度，不用 `toFixed(5)`。
3. 探测用 GET，不用 HEAD；或 app 补 `do_HEAD`。
4. targets 删掉本地副本，读 app/DB。
5. 覆盖统计按 `exposures` 而非 detector rows；与 DB 同一半径常量。
6. 若两天内修不完：从演示路径移除，只作为“天区上下文”截图讲。

### 阶段 4：工程工具（1–2 天）

1. 验收/契约工具（P0）。
2. 离线冻结 + 启动器（P1）。
3. 头文件采集器（P1，若要讲“持续更新”加分项）。
4. 数据漂移检查（P2，可并入验收）。

## 10. 架构决策记录（ADR）

| ID | 决策 | 理由 | 代价 |
|---|---|---|---|
| ADR-001 | 数据库是唯一数据源；app/view 只读 | 消除 3 份 targets、2 套历元 | 需要接线与契约测试 |
| ADR-002 | 保留“导出 JSON”作为离线契约，HTTP 作为运行时可选 | 不破坏 app 现有运行；演示可离线 | 两套路径需同一 schema 校验 |
| ADR-003 | `coverage_level` 与 `analysis_readiness` 分离 | 覆盖≠检测；WISE/Barnard/RW 已证明会冲突 | UI 要解释两个指标 |
| ADR-004 | 覆盖默认半径 2.47°（半对角线），422 作为最终裁决 | 1.745° 会丢 Barnard 204 天基线和 RW Aur 唯一历元 | 可能多查一些帧，需要 422 过滤 |
| ADR-005 | 视图工具降级为可选伴侣，不进入验收硬路径 | 它不渲染 FITS、不参与测量；交接链已断 | 少一个“炫技”点，但降低风险 |
| ADR-006 | 新增控制面工具，而不是第四个产品 | 缺的是验收/冻结/采集/启动，不是再一个 UI | 需要 3–5 人天工程投入 |
| ADR-007 | 所有降级必须带 `fallback_reason`，禁止静默 | 当前“断网写成基线不足”会误导评委 | 需要改 app 的 data/motion 与 UI |

## 11. 契约测试清单（交给验收工具执行）

- [ ] `Target` 7 条逐字段一致（app / DB / view）。
- [ ] `EpochRef` 十字段非空；`date_obs` 非空；无重复 `(obsid,detector)`。
- [ ] `target_id=barnard` 与 `ra/dec` 返回同一组 4 条历元。
- [ ] `target_id=rw_aur` 与 `ra/dec` 都返回 1 条真实历元。
- [ ] `coverage.radius_deg` 默认 2.47；`coverage_level` 存在且不是 `L*`。
- [ ] `AnalysisResult.schema_version`、`data.provenance`、`data.fallback_reason`、`result.readiness_scope` 存在。
- [ ] `mode=real` 的 `epochs[].provenance` 全为 `real`；`mode=hybrid` 至少一个 real 组件。
- [ ] `FETCH_FAILED` 不被写成 `BASELINE_TOO_SHORT`。
- [ ] `/api/health` 三个服务都支持 GET，且 `schema_version` 一致。
- [ ] 任何 UI 暴露的模式不返回 500；非法参数返回 400。
