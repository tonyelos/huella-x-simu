# 03 · 额外工具建议（Build / Don't Build）

> 问题：现有三个工具够不够？还需要开发额外工具吗？
> 结论：**需要，但不是第四个产品，而是控制面的三类工程工具 + 一条运行时接口。**
> 快照：2026-11-14 23:07 CET；迁移：2026-11-14 23:52 CET。`app/`、`数据库工具/`、`视图工具/` 等已移入 `系统/`，本文路径为设计时点。

---

## 0. 先分清两类“工具”

| 类型 | 是什么 | 现有 | 缺什么 |
|---|---|---|---|
| **产品工具**（给评委/公众用） | 有 UI、有叙事、进演示 | MoveScope（主）、视图工具（可选） | 不需要再加一个 UI |
| **工程工具**（给团队用） | 保证产品可验收、可复现、可离线、可更新 | 数据库 CLI、`find_epochs.py`、`scan_week_index.py`、`validate_pipeline.py` | 验收/契约、数据桥、离线冻结、头文件采集、统一启动 |

**判断标准**：如果缺的是“让现有工具正确协作/可证明正确”，就开发工程工具；如果缺的是“再做一个页面/再存一份数据”，就不要开发。

## 2. T1 · 验收与契约工具（P0，最该先做）

### 为什么

现在的“验证”只有 `tools/validate_pipeline.py`：5 目标 × 8 种子 = 40 次**合成注入-回收**，分类 100%。它证明的是“算法在已知真值下能工作”，**不证明**：

- HTTP API 在 5 个目标上都返回合法 schema；
- UI 的 BIC/历元面板真的可见；
- 任意坐标会走真实数据；
- 断网时不会把失败伪装成“基线不足”；
- 数据库导出与 app JSON 仍然一致；
- 视图工具深链真的能打开正确目标。

所以需要一个**只给团队用、不对外**的验收工具。

### 输入 / 输出

```text
输入：
  - 三工具源码 + 数据快照
  - 项目主控/contracts/v1/*.schema.json
  - 项目主控/contracts/golden/*.json
输出：
  - report.json       机器可读：每条用例 PASS/FAIL/WARN + 证据
  - report.md         人读：表格 + 失败复现命令
  - screenshots/      5 目标 × 闪烁/叠加/相减/轨迹
  - artifacts/        API 响应、DB 导出、日志
退出码：0 全过；1 有 P0；2 环境错误
```

### 用例集（最小可用）

| 组 | 用例 | 判定 |
|---|---|---|
| A. 契约 | `Target` 7 条逐字段一致；`EpochRef` 十字段非空；`date_obs` 非空；无重复 `(obsid,detector)` | 任一失败 = P0 |
| B. 导出对账 | `cli.py export all` + `check_compat.py` 四项 OK | 失败 = P0 |
| C. 5 目标 HTTP | 5 × `POST /api/analyze`：200、schema、`mode/provenance` 自洽、`readiness/class` 在黄金容差内、耗时 < 30 s | 任一 500 = P0；class 变化 = WARN |
| D. 任意坐标 | ① Barnard 精确坐标 → REAL 4 期 ② RW Aur → 1 条真实历元 ③ 未覆盖天区 → 明确 `NO_LOCAL_COVERAGE` ④ 断网 → `FETCH_FAILED` | ①–④ 任一不符 = P0 |
| E. 错误路径 | `mode=sample` 不 500；`fov=-0.2` 返回 400；`fov=0` 返回 400；`target_id` + 冲突 ra/dec 返回 400 | 任一 500 = P1 |
| F. UI | 打开 5 目标；BIC 面板可见；历元列表非空；控制台无 error；深链 `?target=` 打开正确目标 | 任一失败 = P1 |
| G. 离线 | 断网/黑洞代理；5 目标从缓存跑通；`FETCH_FAILED` 不伪装 | 失败 = P0 |
| H. 三服务健康 | `/api/health` GET 200；`schema_version` 一致；端口不冲突 | 失败 = P1 |
| I. 数据完整性 | `cli.py verify --deep`：0 missing/0 corrupt；`header_available` 与事实一致 | 失败 = P1 |

### 验收标准（工具本身的 DoD）

- 一条命令：`项目主控/验收/run.sh`（或 `make accept`），< 5 分钟。
- 不修改三工具源码；只读 + 临时目录。
- 失败必须打印**可复现命令**和**期望/实际**。
- 黄金样本带容差（μ ±5%、PA ±5°、class 严格），避免每次微调都“红”。
- 报告可直接贴进提交材料/答辩。

### 工作量

1.5–2.5 人天（含 5 目标黄金样本、截图、离线模式）。这是 P0 里性价比最高的。

## 3. T2 · 数据桥接（P0，不是新服务）

### 为什么

R1 的断点不在“没有数据”，而在“app 的 custom 分支不查数据”。数据库已经有 `frames`、`target_epochs`、cone、coverage、blob；缺的是一条**规范、可测的运行时接口**。

### 形态选择

| 方案 | 评价 |
|---|---|
| A. app 直接读 `catalog.sqlite` | ❌ 跨工具耦合，且 app 只该依赖 HTTP/JSON |
| B. app 调 DB HTTP `/api/v1/epochs` | ✅ 推荐；进程隔离，可独立测试 |
| C. DB 导出“任意坐标”JSON | ❌ 坐标空间无限，导出不现实 |
| D. 在 app 内嵌一个 `db_client` 复制 DB 逻辑 | ❌ 第二事实源，必然漂移 |

**推荐 B**：数据库提供规范 DTO；app 加一个极薄的 `epoch_source` 适配层；失败回退到本地 `epoch_catalog.json`（预设目标）或显式 SIM（自定义坐标）。

### 接口契约（与 02 文档一致）

```text
GET /api/v1/epochs?ra=&dec=&fov=&radius=2.47
→ { schema_version, query, coverage{coverage_level, baseline_days},
    epochs[EpochRef], count, generated_at }
```

### app 侧行为（架构规定，不是代码）

```text
resolve_epochs(target, ra, dec, fov, mode):
  1. 若 target 是预设目标：读本地 epoch_catalog.json（现有行为，保持稳定）
  2. 若 target 是 custom 且 mode in (auto, real):
       a. 调 DB /api/v1/epochs
       b. count >= 2 → 真实取数，mode=real
       c. count == 0 → fallback_reason=NO_LOCAL_COVERAGE，SIM（明确标注）
       d. 取数失败 → fallback_reason=FETCH_FAILED，UNAVAILABLE（可重试）
  3. 若 mode == synthetic/sample：按用户意图，不再查 DB
```

### 必须先修的三个数据问题

1. `?target_id` 与 `?ra/dec` 返回同形 DTO（`obsid/key/date_obs/sep_deg`）。
2. 覆盖默认 2.47°，否则 Barnard 丢 204 天、RW Aur 丢唯一历元。
3. `date_obs` 非空（MJD 反推）；否则 UI 的 `ep.date_obs.slice(0,10)` 会崩。

### 验收标准

- 输入 Barnard 精确坐标（无 `target_id`）→ `mode=real`、4 期、L2、S，与预设完全一致。
- 输入 RW Aur 坐标 → 1 条真实历元；不是 0，也不是 HYBRID。
- 输入未覆盖天区 → `NO_LOCAL_COVERAGE` + SIM，UI 明确写“本地无覆盖，以下为模拟演示”。
- 断网 + 有历元 → `FETCH_FAILED`，不出现“基线不足”文案。
- 契约测试 A/C/D 全过。

### 工作量

1–2 人天（DB 规范化 0.5–1；app 适配 0.5–1；测试 0.5）。**不做这个，R1 永远是 FAIL。**

## 4. T3 · 离线演示冻结器（P1）

### 为什么

- IRSA 历史上 TAP/SIA/DataLink 全 502；演示当天不能赌网络。
- 当前 `app/data/epochcache` 有 55 个 NPZ、15 个 pointing 区域，覆盖 Barnard / Eps / WISE / M101 / 场 A；RW Aur、R Dra 没有真实切片（走模拟，不需要网络）。
- **已实测**：阻断 `urllib` 后跑完整管线，5/5 成功，结果与在线一致。所以 T3 不是“从零做离线”，而是把隐式缓存变成**可校验、可移植、可冻结**的快照。
- 演示还需要“2 个自定义坐标”的离线覆盖，这部分目前没有。

### 形态

不一定要独立服务；可以是验收工具的一个子命令：

```text
freeze --targets all --coords "269.45,4.69;133.80,-7.25" --out demo/snapshot-2026-11-14
verify --snapshot demo/snapshot-2026-11-14 --offline
```

产物：

```text
demo/snapshot-<date>/
  manifest.json      # target, ra/dec/fov, epochs[], url, sha256, bytes, fetched_at
  epochs/*.npz       # 或从 app/data/epochcache 复制 + 校验
  results/*.json     # 冻结时的 API 结果（黄金基线）
  README.md          # 如何离线启动
```

### 验收标准

- 断网（或 `HTTPS_PROXY=127.0.0.1:9`）下，5 个目标全部 `HTTP 200`，每个 < 5 s。
- `manifest` 的 sha256 与文件一致；缺一个就 fail。
- 页面不出现“取数失败”；`mode/provenance` 与冻结时一致。
- 冻结包可拷贝到另一台机器直接跑。

### 工作量

0.5–1 人天（复用现有缓存 + 一个清单/校验脚本）。

## 5. T4 · 头文件采集器（P1，取决于是否讲“持续更新”）

### 为什么

- `app/data/header_cache/` 已被删除；数据库 `header_frames=0`；`date_obs`/`naxis`/`pixel_scale`/`crpix`/`sip_order`/`psf_fwhm`/`l2dqa` 全空。
- `frames` 94.6% 是 D1，无法支撑多波段/彩色故事。
- 数据库声称“增量更新”，但没有“新头文件从哪来”的工具；`find_epochs.py` 只取目标附近，`scan_week_index.py` 每周只取一个头。
- 官方加分项 B1（跟上数据发布）需要它。

### 形态

```text
harvest_headers --release dr1 --weeks 2026W40,2026W41 \
  --prefix <可选> --out app/data/header_cache \
  --manifest app/data/header_manifest.json \
  --workers 8 --resume
```

要求：

- 只读 S3 Range（前 ~64 KB），不下载 65 MB 整文件。
- 增量：已存在且 sha256 匹配则跳过；断点续跑。
- 记录 `release/week/version/obsid/detector/bytes/sha256/fetched_at`。
- 限速/重试/退避；失败清单单独输出。
- 采完自动 `ingest headers`，填 `header_sha256`、`date_obs`、`pixel_scale` 等。

### 验收标准

- 目标周的头文件 100% 落盘，manifest 与 `db.header_frames` 一致。
- 重跑幂等（0 新增，0 重复 Blob）。
- `verify --deep` 通过；`date_obs` 非空率 100%。
- 至少覆盖 5 个官方目标的所有历元（74 条）对应头。

### 工作量

1.5–2.5 人天（S3 列举 + Range + 重试 + 清单 + 入库）。如果时间不够，**优先只采 74 条历元对应的头**，不做全量 14k。

## 6. T5 · 统一启动器（P1）

### 为什么

- app 默认 8765、README 写 8790；视图 `start.sh` 扫 8790–8829，必撞；数据库 8797。
- 演示时三套命令、三个终端、手动检查 health；一旦端口错，前端 fetch 全 404。
- 视图工具的 `HEAD` 探测失败，部分原因也是服务/路径不对。

### 形态

```text
项目主控/start_all.sh          # 固定端口，启动 app 8790 + DB 8797 + view 8830
项目主控/stop_all.sh
项目主控/health.sh             # 三服务 /api/health + 端口 + 数据快照
```

要求：

- 端口固定，不扫描；被占用时明确报错，不偷偷换端口。
- 启动顺序：DB → app → view；每个都等 health 通过再下一个。
- 打印三个 URL + 数据快照 + git commit。
- 日志集中到 `项目主控/logs/`。
- `stop_all` 只杀自己启动的 PID。

### 验收标准

- 一条命令，30 s 内三服务全绿。
- 重复执行不产生孤儿进程；`stop_all` 后端口全释放。
- 端口被占时给出可操作的提示（谁占的、怎么改）。

### 工作量

0.5 人天。

## 7. T6 · 漂移检查器（P2，建议并入 T1）

检查项：

- targets：三处逐字段（含 `coord_unc_arcsec`）。
- epochs：app JSON vs DB `target_epochs` vs 导出；74/74。
- fields：视图 `fields.json` vs DB `frames`；5,857/5,857。
- 常量：覆盖半径、L3 基线阈值、去重容差、端口。
- 就绪度：`coverage_level` vs `analysis_readiness` 的映射是否被误用。
- 文档：README/INTEGRATION 中的数字与实测是否一致（27 tests、5,544 exposures、schema v4）。

落地方式：`check_compat.py` 已覆盖导出；再加一个 `check_consistency.py` 即可，不必独立产品。

工作量：0.5 人天（在 T1 里做）。

## 8. 明确不建议开发的东西

| 提案 | 为什么现在不做 |
|---|---|
| 第四个产品 UI / 另一个 3D 地球 / 另一个闪烁器 | 视图工具已经证明“好看但不进验收”；再加一个只会增加维护面 |
| 第二个数据库 / 把 SQLite 换 Postgres | 5,857 帧、4.3 MB；SQLite 足够；换库不解决 R1 |
| 完整光谱 / 102 波段合成 | 官方加分项，但需要大切片/整幅图，成本和演示风险高；先把 R1 做对 |
| Gaia/WISE 叠加 | 加分项；外部依赖 + 坐标匹配，短期不划算 |
| 盲搜索 / track-before-detect | 研究级；5 个已知目标不需要；会拖垮进度 |
| 用户系统 / 云部署 / 鉴权 | 本地演示不需要；公网再谈 |
| 用 LLM 做“自动判读” | 现有 BIC + 规则可解释、可证伪；不要引入不可复现的黑箱 |

## 9. 路线图与工作量

| 顺序 | 任务 | 工具 | 工作量 | 通过标准 |

## 10. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| R1 接线时发现 DB 覆盖不足（只有 15 周） | 高 | 中 | 明确“本地覆盖内真实、覆盖外诚实 SIM”；同时保留网络发现 |
| 修 DB API 破坏导出兼容 | 中 | 高 | `check_compat.py` 作为门禁；先加 v1 端点，不改旧端点 |
| 视图工具深链修复后仍因坐标精度失败 | 高 | 中 | 传 `target_id` 或全精度坐标；禁用 `toFixed(5)` |
| 演示当天 IRSA 502 | 中 | 高 | T3 离线冻结；默认离线启动 |
| 并行编辑导致验收基线漂移 | 高 | 高 | git + 冻结 + 验收只认 tag |
| 头文件采集耗时/被封 | 中 | 中 | 只采 74 条历元；Range + 退避 + 清单 |
| 工作量超 3 天 | 高 | 中 | 砍 T4/T5/视图；保 R1 + 验收 + 离线 |

- [ ] R1：任意坐标在本地覆盖内返回真实多期图像；覆盖外明确标注 SIM，不冒充。
- [ ] R2：5 目标都能播放；4 种显示模式可用。

- [ ] 契约：`/api/v1/epochs` 两入口同形；`date_obs` 非空；无重复。

- [ ] 工程：一条命令启动、一条命令验收、git tag 可回滚。
- [ ] 文档：所有数字与实测一致；已知限制写清楚。
