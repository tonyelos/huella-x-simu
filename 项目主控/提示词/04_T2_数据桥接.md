## 任务

### T1. 新增 `app/core/epoch_source.py`

建议接口（可调整命名，但语义必须一致）：

```python
@dataclass
class EpochResolution:
    epochs: list[dict]          # 规范 EpochRef
    coverage: dict | None       # n_epochs / baseline_days / coverage_level / ...
    matched_target_id: str | None
    fallback_reason: str | None # DB_UNAVAILABLE / NO_LOCAL_COVERAGE / ...
    source: str                 # "db" | "local_json" | "none"

def resolve_epochs(
    ra: float, dec: float, fov: float,
    target_id: str | None = None,
    *, base_url: str | None = None, timeout: float = 2.0,
) -> EpochResolution: ...
```

要求：

- `base_url` 默认读环境变量 `SPHEREX_DB_URL`，再默认 `http://127.0.0.1:8797`。
- `GET {base}/api/v1/epochs?ra=&dec=&fov=`；若 `target_id` 给的是预设目标，可优先 `?target_id=`。
- 超时 2 s，1 次重试；连接失败/非 200/JSON 错误 → `DB_UNAVAILABLE`，不要抛到 HTTP 500。
- 校验 DTO：缺 `key/obsid/date_obs` 的条目丢弃并记 warning；`date_obs` 为空时由 `mjd` 反推 UTC。
- 去重 `(obsid, detector)`；稳定排序 `mjd, detector`。
- 不缓存跨请求的坐标结果（除非你加 TTL 且有失效）；数据库是事实源。
- 单元测试：正常、空、超时、坏 JSON、缺字段、date_obs 回填。

### T2. app 侧“已知目标匹配”

目的：用户手动输入 Barnard 坐标（不带 `target_id`）时，仍能使用 Barnard 的真值/坐标不确定度，从而与预设结果一致。

- 在 `epoch_source.py` 里实现 `match_known_target(ra, dec, tol_deg=0.05)`，读 `app/data/targets.json`（或 DB `/api/targets` 回退）。
- 命中时：
  - 优先使用 DB 响应里的 `matched_target_id`；DB 没给或 DB 不可用时，再用本地 0.05° 匹配；
  - `matched_target_id` 返回目标 id；
  - 使用目标的 `truth`（自行/视差）做历元位置传播；
  - 使用目标的 `coord_unc_arcsec` 做关联半径；
  - UI 显示“匹配到 Barnard's Star（官方目标）”，但仍保留用户输入的坐标作为查询中心。

- 不要修改 `app/data/targets.json` 的内容。

### T3. 改造 `build_dataset` / custom 分支

当前 `run_analysis` 的 custom 分支只调 `generate_epochs()`。改为：

```text
if target is custom and mode in (auto, real):
    res = resolve_epochs(ra, dec, fov, target_id=None)
    if res.epochs:
        target = merge(target, matched_target_id truth/coord_unc)
        epochs = fetch_real_epochs(res.epochs, ra, dec, fov)   # 复用 fetch_epoch
        if len(epochs) >= 2:
            mode = "real"; fallback_reason = None
        elif len(epochs) == 1:
            mode = "hybrid"; fallback_reason = "INSUFFICIENT_EPOCHS"
        else:
            mode = "unavailable"/"synthetic"; fallback_reason = "FETCH_FAILED"
    else:
        mode = "synthetic"; fallback_reason = res.fallback_reason or "NO_LOCAL_COVERAGE"
```

要求：

- 复用现有 `fetch_epoch()`，不要另写取数；缓存键/原子性由 01 负责。
- 取数位置必须使用与预设路径相同的 `apparent_position(target, mjd)`（目标 truth 传播），这样能命中同一 NPZ 缓存，保证“手动输入 Barnard 坐标”与“点预设”结果一致、离线也可用。
- `fetch_epoch` 返回 None 时，记录成功/失败数量；**note 必须基于成功取回的期数，不是目录期数**。
- `baseline_days` 用成功取回的历元计算；不要用目录的 `real_days` 冒充。
- 真实历元 ≥2 且 `baseline_days >= 30` → real；否则按 02 的降级矩阵。
- 若 `mode=real` 且一条都取不到 → 返回 200 + `mode=unavailable` + `fallback_reason=FETCH_FAILED` + `result.class=U`，不要把 SIM 标成 real；UI 显示可重试提示。
- 预设目标（`target_id in 7`）继续走现有本地 `epoch_catalog.json`，不要改；保证 5 目标不回归。

### T4. 新增 `fallback_reason` 与 provenance

在 `/api/analyze` 响应里加：

```json
{
  "data": {
    "mode": "real",
    "provenance": ["real"],
    "fallback_reason": null,
    "n_epochs": 4,
    "real_epochs": 4,
    "note": "..."
  }
}
```

`data.real_epochs` 是**成功取回的真实像素期数**，必须与 `n_epochs`（参与分析的期数，可能含模拟）区分。RW Aur 只有 1 条真实历元时，`real_epochs=1`、`mode=hybrid`，不能写成 0。

`fallback_reason` 枚举：

- `null`
- `DB_UNAVAILABLE`
- `NO_LOCAL_COVERAGE`
- `INSUFFICIENT_EPOCHS`
- `BASELINE_TOO_SHORT`
- `FETCH_FAILED`
- `TARGET_TOO_FAINT`

规则：

- `mode=real` → `provenance` 全 `real`，`fallback_reason=null`。
- `mode=hybrid` → 至少一个真实组件（背景/PSF/1 条真实历元），`fallback_reason` 说明原因。
- `mode=synthetic` → `fallback_reason` 不能为空（除非用户主动选 `mode=synthetic`）。
- `FETCH_FAILED` 不得写成 `BASELINE_TOO_SHORT`。
- UI：`app/web/app.js` 的 badge/note 显示 `fallback_reason` 的可读中文；`date_obs` 为空时不要 `.slice()` 崩。

### T5. app 的 GET `/api/epochs?ra=&dec=&fov=`
