## 4. 推荐顺序

```
第 1 组（可并行）
  ├─ 01 MoveScope 修复（app 仓库）
  ├─ 02 数据库契约化（DB 仓库）
  └─ 03 视图工具交接（view 仓库）

第 2 组（依赖 01 + 02）
  └─ 04 T2 数据桥接（app 侧 R1 接线）

第 3 组（可并行）
  ├─ 05 T1 验收工具（可在第 1 组就开始搭骨架）
  ├─ 06 T3 离线冻结
  ├─ 07 T5 启动器
  └─ 08 T4 头文件采集（可选，取决于是否讲“持续更新”）
```

**如果只有 1–2 天**：只做 **02 → 04 → 05 的 R1 用例**。R1 是官方硬要求；其他都可后置。

**如果要并行**：01 与 02 不同仓库，安全；03 不同仓库，安全；04 必须等 01/02 完成，否则会冲突 `app/core/data.py` 与 `app/server.py`。

## 5. 所有执行者都必须遵守的规则

1. **只改自己工作包里的文件。** 不要“顺手修”别的工具；跨工具改动先回到项目主控。
2. **不新增运行时依赖。** app 只允许 stdlib + numpy + Pillow；DB 只允许 stdlib；视图工具只允许现有 three.js；验收/冻结/启动器只允许 stdlib（需要浏览器截图时另建可选步骤）。
3. **不为了让 5 个目标“好看”而放宽显著性/阈值。** 诚实标记 REAL/HYBRID/SIM、L0–L3、可证伪条件是产品能力。
4. **不改数据事实源。** app 不写 DB；DB 不写 app JSON；view 不维护第二份 targets。
5. **所有降级必须显式。** 新增 `fallback_reason`/`provenance`/`quality`，不允许静默把失败写成“基线不足”。
6. **改完必须实际运行验收命令**，把命令、输出、前后对比写进交付说明；没有运行证据的“已修复”不算。
7. **以当前代码为准。** 提示词里的行号/数字可能漂移；若发现与代码不符，先记录，再按代码修。
8. **不要提交半成品。** 若时间不够，交付“可回滚的最小闭环 + 未完成清单”，不要留下 500 或死代码。
9. **中文 UI/文档。** 代码注释可用英文；用户可见文案用中文。
10. **不要改 `项目主控/` 里的审计结论**；如需更新状态，另写 `项目主控/验收/report-*.md`。
