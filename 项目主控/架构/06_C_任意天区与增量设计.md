## 0. 一页结论

C 要解决的不是“全天实时巡天服务”，而是：

> **给定任意 RA/Dec/FOV，先诚实回答本地有没有真实历元；有就按需取数并给出可复现的多历元数据；没有就明确 `NO_LOCAL_COVERAGE`，让上层显示 SIM；新历元可以幂等追加，追加后只重算受影响的测量与时间序列。**

### 0.1 关键决策（后续实现按此执行，除非 lead 明确改）

| # | 决策 | 理由 |
|---|---|---|
| D-C1 | C 推荐做成**独立数据平面服务**（建议端口 `8798`，路径 `系统/anyfield/`），只读现有 `catalog.sqlite`，写独立的 `var/anyfield.sqlite` + `var/cache/` | 现有 DB API 是只读元数据服务，明确“不在服务端实时下载 IRSA”（`数据库工具/docs/DESIGN.md` §8）；app 是科学分析/UI。把网络下载、长任务、写测量塞进任一现有进程都会破坏其边界 |
| D-C2 | **本地优先，按需第二，绝不伪造**；`/api/v1/field` 只在“本地索引对该天区完整且确认无历元”时返回 **422 `NO_LOCAL_COVERAGE`**；索引不完整或上游失败返回 **503 `FIELD_UPSTREAM_UNAVAILABLE` / `INDEX_INCOMPLETE`**，不能把“不知道”说成“没有” | 422 是强断言；错误地 422 会让用户以为天空没数据，比 503 更糟 |
| D-C3 | 覆盖判定用**真实足迹（WCS 四角/多边形）**，不再只拿 `frames.ra/dec` 中心 + 2.47° 半径当覆盖；legacy `/api/v1/epochs` 的 2.47° 字段保持不变以过 T1 | 现有 `COVERAGE_RADIUS_DEG=2.47` 是半对角线近似，既可能把方形角外算进来，也可能漏掉边缘；C 必须能解释“为什么这块没覆盖” |
| D-C4 | 全量索引只存**元数据**（键、时间、中心、足迹、头校验），不镜像 65 MB 像素；头用 S3 Range 64 KB；像素按需切片并内容寻址缓存 | 全 151 周像素约 2.5 TB，本地已有 5,893 帧全量也约 383 GB；镜像不可分发、不可备份 |
| D-C5 | release/version 是身份的一部分：`epoch_id = sha256(release\|version\|obsid\|detector)`；**QR3 与 DR1 不混在同一条测光时间序列**；DR1 可用时优先 DR1，QR3 只补 DR1 没有的新历元 | 两个处理版本的 PSF/定标不同；混拟合会制造假运动/假变光 |
| D-C6 | 增量 ingest 用**异步任务 + 阶段状态机 + 原子发布**；已发布后的“重算序列失败”不回滚原始测量，只标 `series_stale` 重试；人工回滚用软撤回（`retracted_at`） | 原始数据和派生产物生命周期不同；为了派生失败丢掉已到手的真实数据不可接受 |
| D-C7 | `/api/v1/epochs` **保持 `schema_version="1.0"` 和现有 12 个 EpochRef 字段**，只做加法；`/api/v1/field` 是新端点并承担 422；`/api/v1/ingest` 返回 202 异步任务 | T1 验收硬性要求 `schema_version="1.0"`、EpochRef 十字段、coverage `radius_deg=2.47`；不能在 C 里破坏 A/B 已通过的契约 |
| D-C8 | C **不生成 SIM**；C 只给真实历元/覆盖/任务状态。SIM 由 app 依据 `NO_LOCAL_COVERAGE` 显式生成并打 badge | 保持“不把模拟数据伪装成真实观测”的铁律；C 若偷偷回退 SIM，无法审计 |
| D-C9 | MVP 的**像素分析 FOV 上限 0.5°**；`/api/v1/field` 规划可到 3.0°；`include=pixels` 且 FOV >0.5° 时明确 400 `FOV_TOO_LARGE_FOR_PIXELS`，或由上层改用规划/分块 | 0.5° 切片四数组约 1.4 MB + EPSF 3.86 MB（约 5.2 MB）；3.0° 四数组约 49 MB + EPSF 约 53 MB，8 期不可接受。3.0° 的 SIM/展示仍由 app 现有能力承担 |
| D-C10 | 本轮**不做**上传、不做全量索引实测、不做 B 批量匹配实现、不写生产 DB schema 迁移；这些留给 4–8 周实现阶段 | 本轮目标是设计/接口/spike 计划，不制造半成品 |

### 0.2 一句话边界

- 任意天区：**支持**；但不承诺每个天区都有数据。
- 多历元：**支持**；但历元数量/基线由真实覆盖决定，C 不造。
- 新图增量：**支持设计**；官方新 release/新周为主，用户上传为可选后续。
- 全天实时：**不承诺**；SPHEREx 本身是每 6 个月扫全天，且本地 DB 只有部分周。
- 已知/未知：**不做**；C 只给测量与 provenance，D 做分类。

## 1. 目标 / 非目标

### 1.1 目标（可验收）

| ID | 目标 | 可量化口径 |
|---|---|---|
| G1 | 任意 RA/Dec 查询真实历元 | 0.02° ≤ FOV ≤ 3.0° 的规划查询；有效输入 100% 返回结构化结果，不 500 |
| G2 | 多历元与时间基线诚实 | 返回 `n_epochs`、`n_observations`、`baseline_days`、`coverage_level` C0–C3；覆盖不足时明确 C0/C1 |
| G3 | 无覆盖不等于 500，也不等于 SIM | 确认无覆盖时 `/api/v1/field` 返回 422 `NO_LOCAL_COVERAGE`；app 显示 SIM badge；真实数据响应绝不带 `provenance=synthetic` |
| G4 | 新历元可增量 | 同一新图重复 ingest 不新增行；成功 ingest 后 measurement +N、受影响 series revision +1；失败注入不留下可见半成品 |
| G5 | 可复现 | 每个响应带 `index_snapshot`、`dataset_version`、`pipeline_version`、`release/version`；同一快照 + 同一请求返回同一 `field_id` |
| G6 | 可运维 | 本地 p95 ≤ 300 ms；冷启动发现 p95 ≤ 30 s；断网不卡死；429/5xx 有退避/熔断/`Retry-After` |
| G7 | 不破坏现有契约 | `/api/v1/epochs` 仍过 T1；A/B/D 的现有契约不被 C 强制改写 |

### 1.2 非目标

- **不做全天实时**：不承诺任意时刻、任意天区都有当周数据；不承诺秒级刷新。
- **不做全量像素镜像**：不把 151 周 × 6 探测器 × 65 MB 下载到本地。
- **不重做 SPHEREx 官方 pipeline**：不做绝对定标、不重新生成 level2；只做切片、裁剪、重投影和相对天体测量。
- **不做科学分类**：不输出 `known_star` / `uncatalogued` / “新恒星”；这是 D 的职责。
- **不拥有星表**：Gaia/2MASS/WISE 由 B 的服务负责；C 不导入、不复制星表。
- **不跨 release 混测光**：QR3 和 DR1 各自成组；不做“QR3+DR1 一条曲线”。
- **不做用户上传的 MVP**：上传 FITS 只作为后续可选能力，默认关闭；避免把不可信大文件带进公网服务。
- **不承诺发现**：C 不产出“新天体”；只产出可追溯的测量。
- **不修改现有 app/DB**：本轮只在 `tool/anyfield` 写本设计文档。

**重要纠正**：任务背景里的“151 周”是 `week_index.json`/`weeks` 的**扫描索引**（QR3 41 + DR1 110）；`frames` 实际只覆盖 **23 个周**。因此：

- 不能说“本地有 151 周覆盖”；
- 不能把 D1 的 5,548 帧当成“6 探测器都有”；
- 任意天区的大部分查询会落在没有本地帧的周/天区，`NO_LOCAL_COVERAGE` 是常态，不是异常。

### 2.2 现有本地覆盖的粗略量级

用 1° 天球网格、以 `frames.ra/dec` 为中心做距离统计（**不是**真实足迹并集，只用于量级）：

| 半径假设 | 至少 1 帧的天区比例 | ≥2 个 exposure 的比例 | ≥6 个 exposure 的比例 |
|---|---:|---:|---:|
| 1.745°（方形内切圆） | 41.5% | 26.6% | 4.7% |
| 2.47°（方形外接圆） | 52.2% | 41.3% | 13.9% |

推论：

- 随机 20 个天区，预计 **8–12 个**至少有 1 个本地 exposure，**5–8 个**有 ≥2 期；不是“几乎全空”，也不是“全天都有”。
- 这组数字是**中心近似**；真实足迹覆盖率会落在两者之间。spike S3 必须用 WCS 四角校准，不能拿本表当验收真值。
- 20 个随机天区足以同时覆盖“有数据/无数据”两种路径，不需要人为挑 10 个有数据的场；但为了正向路径可重复，另加 10 个已知有覆盖的对照场（见 §10）。

## 3. 总体架构与数据路径

### 3.1 推荐部署形态（D-C1）

```text
┌──────────────────────────┐        ┌──────────────────────────┐
│ app / A（8790）           │        │ D（识别层，后续）          │
│ 交互点选、/api/analyze    │        │ 读 measurement / 分类      │
└────────────┬─────────────┘        └────────────▲─────────────┘
             │ /api/v1/field, /api/v1/epochs      │ 只读导出
             ▼                                   │
┌──────────────────────────────────────────────────────────────┐
│ C · AnyField 数据平面（建议 8798，系统/anyfield/）              │
│  - field resolver：本地索引 → 按需发现 → 覆盖/422              │
│  - epoch index：sidecar SQLite + 快照                          │
│  - fetcher/cache：IRSA 静态切片、S3 Range、TTL/LRU             │
│  - ingest worker：FITS→裁剪→WCS/PSF/FLAGS→重投影→测量→发布    │
└───────┬───────────────────────────────┬──────────────────────┘
        │ 只读                           │ 网络
        ▼                               ▼
┌──────────────────┐        ┌──────────────────────────────────┐
│ catalog.sqlite   │        │ IRSA 静态切片 / S3 nasa-irsa-spherex│
│ 5,893 帧（v6）    │        │ TAP/SIA/DataLink 仅可选降级       │
└──────────────────┘        └──────────────────────────────────┘
        │
        ▼
┌──────────────────┐
│ B catalog 服务    │  C 调 /api/v1/catalog/cone / match
│（独立 8799）      │  B 失败 → C 标记 match deferred，不猜 known/unknown
└──────────────────┘
```

**为什么不把 C 放进现有进程：**

- DB 服务：只读、无网络、无 numpy 科学栈；把 ingest 放进去会破坏“数据库工具不做服务端实时下载”的既有设计（`DESIGN.md` §8）。
- app：分析请求是短生命周期、内存密集；ingest 是长任务、会写状态；混在一起会让 UI 请求被 65 MB 下载/重投影拖死。
- C 独立进程可以单独限流、重启、清理缓存、回滚，不污染现有 5,893 帧基线。

> 部署位置是**建议**而不是不可变契约：如果 lead 决定 C 作为 app 内模块或 DB 扩展，本文的 API/表/流程仍然成立；但必须保留“只读现有 DB + 独立写侧”的边界，不能直接改 `catalog.sqlite` 的生产表。

### 3.2 三条数据路径

| 层 | 做什么 | 数据来源 | 是否阻塞分析 |
|---|---|---|---|
| **L0 本地索引** | 回答“本地有没有历元、覆盖多少” | `catalog.sqlite` + `anyfield.sqlite` 快照 | 否；最快 |
| **L1 按需发现** | 本地没有时，发现候选历元 | TAP obscore（可选）→ `week_index.json` + S3 List + Range 头 → 422 确认 | 可能；有 30 s 预算 |
| **L2 像素取数** | 取真实切片/裁剪产品 | 本地缓存 → IRSA 静态切片 → S3 Range（优化/spike） | 按需；有 60 s 预算 |

**发现（discovery）与取数（retrieval）必须分开**：

- 发现只回答“哪个文件可能覆盖、MJD 多少、release/version 是什么”；
- 取数才下载像素；
- 覆盖判定优先用头/WCS 足迹，422 只作为单文件确认。

### 3.3 路径优先级与降级

```text
本地索引命中（快照完整）
  ├─ 有历元 → 200，返回 EpochRef[]
  └─ 无历元 → 422 NO_LOCAL_COVERAGE（仅当该区域索引完整）
本地索引未命中/不完整
  ├─ 允许联网（mode=auto）
  │   ├─ TAP obscore（≤20 s，1 次重试）→ 命中则入库，200
  │   ├─ TAP 不可用 → week_index（黄经带）→ S3 List → Range 头 → 422 确认
  │   │     ├─ 找到 → 入库（source=ondemand，TTL）→ 200
  │   │     └─ 未找到 → 422（若候选周已扫描完整）或 503 INDEX_INCOMPLETE（未扫完）
  │   └─ 全部上游失败 → 503 FIELD_UPSTREAM_UNAVAILABLE（coverage.state=unknown）
  └─ mode=local（只读本地）→ 422 NO_LOCAL_COVERAGE
```

**关键区分**：

- `422 NO_LOCAL_COVERAGE`：**已验证**“本地/候选周没有覆盖”；
- `503 FIELD_UPSTREAM_UNAVAILABLE`：**不知道**有没有覆盖（TAP/S3 都失败）；
- `503 INDEX_INCOMPLETE`：索引没扫完，不能断言没有；
- `200 partial`：有部分覆盖，可以分析但要显示 `coverage_fraction`；
- 不允许把 503/504 或索引不完整映射成 `NO_LOCAL_COVERAGE`。

### 3.4 失败降级矩阵

| 失败 | 检测 | 行为 | 返回 |
|---|---|---|---|
| 静态切片 422 | HTTP 422 + body 含 overlap 语义 | 该文件不覆盖；跳过；缓存 6 h | 继续下一个候选 |
| 静态切片 404 | HTTP 404 | 键不存在/版本错误；不重试；标记 `key_missing` | 换候选/报 `KEY_NOT_FOUND` |
| 静态切片 429 | HTTP 429 + `Retry-After` | 尊重 `Retry-After`；指数退避；熔断 | 缓存有则 200，否则 503 `RATE_LIMITED` |
| 静态切片 5xx/超时 | HTTP 5xx/URLError | 最多 3 次（0.5/1.5/4.5 s + jitter）；熔断 60 s | 503 `FIELD_UPSTREAM_UNAVAILABLE` |
| 静态切片 200 但读不完 | 长度/异常 | 不缓存半成品；重试 1 次 | 503 |
| S3 List 失败 | 5xx/超时 | 退避；换 TAP；熔断 | 503 |
| S3 Range 返回 200 全文件 | 状态码不是 206 | **不读 body**，按失败处理（防止 65 MB） | 记录 `S3_RANGE_IGNORED` |
| Range 头不足/坏头 | 缺 OBSID/DETECTOR/CRVAL/MJD | 不写索引；记错误；继续 | 跳过该文件 |
| TAP 502/超时 | 5xx/超时 | 不重试超过 1 次；降级 S3 | 继续 S3 |
| SIA/DataLink 失败 | 任意 | 不作为关键路径 | 忽略/记录 |
| 本地缓存损坏 | sha 不匹配/JSON 坏 | 删除并重取；不 500 | 重取或 503 |
| B catalog 失败 | 连接/5xx/`CATALOG_UNAVAILABLE` | 不把空匹配当新源；`match_state=deferred` | ingest 仍可提交 measurement |
| 磁盘满 | 写失败 | 停止 ingest；保留已有数据；告警 | 507 `CACHE_FULL` |

### 3.5 S3 Range 像素优化（可选 spike，不是 MVP 主通道）

静态切片即使 `size=0.02°` 也会带回 EPSF，单次约 3.9 MB。S3 公开桶支持对**完整 65 MB 文件**做 Range，因此可设计一条“按行带取 ROI”的优化路径：

1. 先 Range 读文件头（`bytes=0-65535`，或按需读到 `IMAGE` 头结束），解析 HDU 顺序/`NAXIS/BITPIX`，算出 `IMAGE/FLAGS/VARIANCE/ZODI` 的数据偏移。
2. FITS 数据按行优先连续存储；目标矩形只需读覆盖其 `y0..y1` 的整行带：
   - 每行 `NAXIS1 × abs(BITPIX)/8` 字节；
   - 对每个数组发 `Range: bytes=<offset+y0*row_bytes>-<offset+(y1+1)*row_bytes-1>`；
   - 本地按 `x0..x1` 裁列，得到 ROI。
3. 估算（2040 px/行，4 字节/像素，4 个数组）：
   - 0.02°（12 行）：约 0.39 MB，对比静态切片 3.9 MB；
   - 0.1°（59 行）：约 1.9 MB；
   - 0.2°（118 行）：约 3.8 MB，与静态切片持平，不再有优势。
4. 适用条件：
   - FOV ≤0.1°、目标远离边缘、头解析成功；
   - 只用于 `IMAGE/FLAGS/VARIANCE/ZODI`；`WCS-WAVE`/`EPSF` 另取或走静态切片；
   - 任一 Range 返回 200（服务器忽略 Range）或字节数不符 → 立刻回退静态切片，不拼接半成品。
5. 验收：同一文件、同一 ROI，S3 Range 结果与静态切片裁剪结果逐像素一致（允许字节序/缩放差异为 0）；延迟 p95 优于静态切片 30% 才启用。

**结论**：MVP 仍以 IRSA 静态切片为主通道；S3 Range 只作为“小 FOV/断点续传/带宽优化”的 spike，不改变 §3.3 的主链。

## 4. 覆盖判定与 422

### 4.1 覆盖 DTO（`/api/v1/field`）

```json
{
  "coverage": {
    "state": "covered | partial | none | unknown",
    "fraction": 0.98,
    "n_epochs": 5,
    "n_observations": 5,
    "n_weeks": 3,
    "n_releases": 1,
    "releases": ["dr1"],
    "detectors": [1, 2],
    "mjd_min": 60789.750762,
    "mjd_max": 61316.529902,
    "baseline_days": 526.78,
    "coverage_level": "C3",
    "radius_deg": 0.1,
    "index_completeness": "complete | partial | unknown",
    "coverage_radius_legacy_deg": 2.47,
    "method": "footprint_v1"
  }
}
```

- `fraction`：请求区域被真实足迹并集覆盖的面积比例（0–1）。
- `state=covered`：`fraction ≥ 0.95` 且 `n_epochs ≥ 1`。
- `state=partial`：`0 < fraction < 0.95` 且 `n_epochs ≥ 1`；可分析，但必须显示“只覆盖一部分”。
- `state=none`：`fraction == 0` 且 `index_completeness=complete`。
- `state=unknown`：索引不完整或上游失败；**不得**返回 422。
- `coverage_level` 沿用 DB C0–C3（观测机会），与 app 的 L0–L3（分析就绪度）严格分开。

### 4.2 足迹算法（`footprint_v1`）

1. 从帧头/WCS 取 `NAXIS1/2`、`CRPIX`、`CRVAL`、`CD/PC`、SIP 系数。
2. 计算四角（含 0.5 px 保守内缩）在天球上的位置；对 SIP 用正变换；四角连成球面凸多边形。
3. 请求区域：
   - 点目标：半径 `max(0.5″, fov/2)` 的小圆；
   - 有限视场：边长 `fov_deg` 的方形（与 app 的 `fov` 语义一致），四角做球面插值。
4. 在请求区域上取采样网格：
   - `fov ≤ 0.02°`：中心 1 点；
   - `0.02° < fov ≤ 0.2°`：9×9；
   - `0.2° < fov ≤ 0.5°`：17×17；
   - `> 0.5°`：仅规划，25×25 或蒙特卡洛 2,000 点。
5. 对每个采样点，判断是否落在任一帧足迹内；`fraction = 命中数 / 采样数`。
6. `n_epochs`：按 `obsid` 去重；一个 exposure 的多个探测器只算 1 个观测机会，但 `detectors` 保留全部。
7. `baseline_days = max(mjd) - min(mjd)`；C0–C3 规则同 DB。
8. 结果缓存键含 `index_snapshot` + 请求规范化后的 hash；快照变化即失效。

**为什么不用 2.47° 圆**：2.47° 是方形外接圆半径，会把方形角外也当成覆盖；1.745° 是内切圆，会漏掉角。C 的 422 断言必须基于足迹，而不是中心圆。

### 4.3 422 探测（单文件确认）

- 仅对**已知 key** 的候选文件使用；不能拿 422 去“扫全天”。
- 请求：`GET https://irsa.ipac.caltech.edu/ibe/data/spherex/<key>?center=<ra>,<dec>d&size=0.001`。
- 状态：
  - `422` → 该文件与点不重叠；读 0 字节 body（22 字节错误体可丢弃）；
  - `200` → 至少有一个像素重叠；不读大 body（读到 header 后关闭即可）；
  - `429/5xx` → 重试/降级，不把它当覆盖结论。
- FOV 确认：
  - `fov ≤ 0.1°`：中心 1 点；
  - `fov > 0.1°`：中心 + 4 角 + 4 边中点，最多 9 点；任一点 200 → 候选；全部 422 → 不覆盖；混合 → 用足迹算法判定，422 只做证据。
- 缓存：
  - 正结果 7 天；
  - 负结果 6 小时（新周可能补数据，不能永久负缓存）；
  - 键 `(key, ra6, dec6, size=0.001, release, version)`；
  - 索引快照变化或新周入库时，批量清负缓存。
- 局限：
  - 422 只说明“该文件与该点不重叠”，不能说明“全天没有其他文件”；
  - 切片服务故障时 422 也可能来自代理错误；必须同时检查 body/状态语义，不能仅凭状态码。
- 成本：422 的 body 22 字节，但请求仍有 RTT；索引完整时优先用足迹，不用 422 扫。

### 4.4 HTTP 语义

| 情况 | `/api/v1/field` | `/api/v1/epochs`（兼容） | app 行为 |
|---|---|---|---|
| 有覆盖（完整/部分） | 200 + coverage | 200 + epochs | 用真实数据；partial 显示比例 |
| 本地完整、确认无覆盖 | **422 `NO_LOCAL_COVERAGE`** | 200 + `epochs=[]` + `coverage.state=none` | 显式 SIM + badge；`fallback_reason=NO_LOCAL_COVERAGE` |
| 索引不完整、按需未完成 | 503 `INDEX_INCOMPLETE` | 503 `INDEX_INCOMPLETE` | 显示“索引未完成”；可重试；不冒充无覆盖 |
| 上游失败（TAP/S3/IRSA） | 503 `FIELD_UPSTREAM_UNAVAILABLE` | 200 + 空/缓存 + warning | 显示“上游不可用”；可用缓存则用缓存；不冒充无覆盖 |
| 限流 | 429 + `Retry-After` | 429 | 指数退避；不无限重试 |
| 参数非法 | 400 `INVALID_QUERY` | 400 | 提示修正 |
| FOV 超像素上限（仅 `include=pixels`） | 400 `FOV_TOO_LARGE_FOR_PIXELS` | 200（规划） | 改用规划/分块或 SIM |

> **为什么 `/epochs` 不返回 422**：它是 A/B/T1 已依赖的 v1 契约，现有 app 期望 200+空列表来决定 SIM；贸然 422 会破坏 `epoch_source`。`/epochs` 对“确认无覆盖”用 200+空列表，对“不知道”用 503；强断言 422 只放在 `/field`。

## 5. 全量与按需历元索引

### 5.1 两层索引

| 层 | 内容 | 构建方式 | 完整性 |
|---|---|---|---|
| **A. 骨架索引** | release/week/version/detector/obsid/key/MJD（若头可得） | S3 ListObjectsV2（每 week/version/detector 前缀）；151 周；分页 1000 | `discovered`；无坐标 |
| **B. 头/足迹索引** | CRVAL、四角、NAXIS、PSF、L2DQA、MJD、DATE-OBS | S3 Range 64 KB 解析 IMAGE 头；或 TAP obscore 批量 | `header_ok`；可做空间查询 |
| **C. 快照** | 以上两层的不可变版本 + manifest sha256 | 构建完成后 `status=active` | `complete`/`partial` 按 week/detector 标记 |

不要求 A 层一开始就全量；本地 5,893 帧 + 74 目标历元可以先构成“bootstrap 快照”，其余按需补。

### 5.2 全量索引构建（建议后台/离线）

1. 列出 `dr1/level2/`、`qr3/level2/` 的周目录（151 个）。
2. 对每个 `(release, week)`：
   - 列出 version 目录（`delimiter=/`）；
   - 对 D1–D6 列出对象键（`max-keys=1000`，翻页）；
   - 用文件名正则提取 `obsid`、`detector`、`version`；写入 `epoch_index(state=discovered)`。
3. 对每个键做 64 KB Range 读头（并发 4，S3 8）：
   - 必填：`OBSID`、`DETECTOR`、`CRVAL1/2`、`MJD-OBS`、`NAXIS1/2`、`CTYPE1/2`；
   - 可选：`SPS_ELON/ELAT`、`PSF*`、`L2DQA`、`DATE-OBS`、`BUNIT`；
   - 计算 `zone`、`footprint_json`、`header_sha256`；写 `state=header_ok`。
4. 若 TAP 可用：先批量取 `obscore` 的 `obs_id, s_ra, s_dec, t_min, access_url`，跳过对应头；TAP 失败不阻塞。
5. 每个 `(release, week, detector)` 的 `n_keys == n_header_ok` 才把 `index_week_state.state=complete`；否则 `partial`。
6. 构建完成写 `index_snapshot`，计算 manifest sha256；`status=active`；旧快照保留 30 天。
7. 增量：新周/新 version 只追加新键；不改旧快照；发布新快照指针。

**全量索引的完整定义**：不是“跑完脚本”就算 complete，而是 `index_week_state` 对每个候选周/探测器都 `complete`。任何未完成区域，`/field` 只能给 `index_completeness=partial`，不能 422。

**规模估计**（按本地 23 周 5,893 帧外推）：

- 全 151 周约 `5,893 / 23 × 151 ≈ 38,700` 帧；
- 全量像素 65 MB/帧 ≈ **2.5 TB**（不镜像）；
- 元数据约 0.5 KB/帧 ≈ **19 MB**；
- 64 KB 头约 **1.55 GB**（若全采；可只采候选周）；
- 因此：元数据索引完全可行；头可分批；像素只按需缓存。

### 5.3 按需发现（本地没有时）

```text
field(ra, dec, fov, epoch_range, release)
  │
  ├─ 1. 本地空间查询（zone/RA 粗筛 + 足迹精判）
  │     └─ 命中足够 → 200
  │
  ├─ 2. 候选周：把 (ra,dec) 转黄经，选 |Δelon| ≤ fov + 3.5° + margin 的周
  │     └─ week_index.json 的 SPS_ELON/SPS_ELAT + release/week
  │
  ├─ 3. S3 List：每个候选周列 D1（必要时 D2–D6）的场号/键
  │     └─ 头 Range 只取中心最近的 N 个候选（N=32，避免全扫）
  │
  ├─ 4. 422 确认：对候选 key 发 center size=0.001
  │     └─ 任一点 200 → 入库为 ondemand 候选
  │
  ├─ 5. TAP obscore（可选，优先于 S3 全扫；20 s 超时）
  │     └─ q3c/CIRCLE 查询 → 直接得到 s_ra/s_dec/t_min/access_url
  │
  └─ 6. 结果写入 sidecar（source=ondemand，TTL 24 h）
        ├─ 找到 → 200，coverage.state=covered/partial
        ├─ 未找到且候选周 complete → 422
        └─ 上游失败/未扫完 → 503
```

**候选周选择**：

- `week_index.json` 每条有 `elon/elat/ra/dec`（实测由 `SPS_ELON/SPS_ELAT` 生成）。
- 查询点转黄经后，按 `|Δelon|` 排序；只取 `fov/2 + 3.5° + 1°` 以内的周。
- 极区（`|dec| > 80°`）黄经过滤失效，直接走 TAP/S3 全周或返回 `INDEX_INCOMPLETE`；不要硬扫 151 周。
- 每个候选周最多读 32 个场头；超过则返回 `INDEX_INCOMPLETE` 并提示“区域候选过多”，由后台继续。
- **422 的前提**：候选周集合本身必须完整。若黄经截断、候选数超过 32 未扫完、极区无法证明候选完整，必须返回 `503 INDEX_INCOMPLETE`，不能 422。

**TAP 查询示例**：

```sql
SELECT TOP 100
       obs_id, s_ra, s_dec, t_min, t_max, access_url, access_estsize
FROM spherex.obscore
WHERE q3c_radial_query(s_ra, s_dec, 269.452077, 4.693365, 0.5) = 1
ORDER BY t_min
```

- 只取元数据；`access_url` 作为候选，不直接当像素 URL 使用（可能是 DataLink/其他形式）。
- TAP 失败：记录 `TAP_UNAVAILABLE`，降级 S3；不重试超过 1 次。
- SIA：不作为 SPHEREx 发现通道；若未来可用，仅作为额外候选，不改变主链。
- DataLink：只在需要由 `obs_id` 换 `access_url` 时尝试；失败则用 §5.4 的路径重建。

### 5.4 路径重建（不依赖 DataLink）

已有实测：

```text
obs_id = 2025W48_1A_0658_4
  → rsplit("_", 2) → week=2025W48_1A, field=0658, repeat=4
  → S3 list qr3/dr1 level2/<week>/ → version（如 l2b-v27-2026-208）
  → key = <release>/level2/<week>/<version>/<detector>/level2_<week>_<field>_<repeat>D<detector>_spx_<version>.fits
  → slice = https://irsa.ipac.caltech.edu/ibe/data/spherex/<key>?center=<ra>,<dec>d&size=<fov>
```

- 必须用 `rsplit("_", 2)`，因为 week 本身含下划线。
- version 从 S3 前缀现查，不硬编码。
- 若 S3 List 失败，仍可用已有 `week_index` 的 `first_key` 模板推断，但必须标记 `version_inferred=true` 并做 422/200 确认。

### 5.5 索引表关键字段（完整 DDL 见附录 A）

- `epoch_index`：`epoch_id` 主键；`release/version/obsid/detector` 唯一；`mjd`、`ra/dec`、`footprint_json`、`zone`、`healpix64`、`key`、`header_sha256`、`source`、`state`。
- `index_week_state`：`(snapshot_id, release, week, detector)` 主键；`state`、`n_keys`、`n_headers`、`last_scan_at`。
- `index_snapshot`：`snapshot_id`、`status`、`complete`、`manifest_sha256`、`n_epochs`。
- `field_query_cache`：`field_key`、`request_json`、`response_json`、`index_snapshot`、`expires_at`。
- `ingest_job` / `ingest_stage` / `ingested_epoch` / `measurement` / `series_revision`（见 §7/附录 A）。

### 5.6 历元身份与去重

- `epoch_id = sha256(release\|version\|obsid\|detector)`；同一曝光的不同探测器是不同 epoch。
- `obsid` 是曝光身份；coverage 的 `n_epochs` 按 obsid 去重，避免 6 个探测器把 1 次观测算成 6 次。
- 同一 obsid + detector + 不同 version（QR3 vs DR1）是**不同 epoch**；默认按 release policy 选一个，不能同时进入一条拟合。
- `superseded_by`：DR1 重处理覆盖 QR3 时，旧 epoch 保留可审计，但默认查询/时间序列使用新版本；`?include_superseded=1` 才返回旧版。
- 同一文件重复发现：`UNIQUE(release, obsid, detector, version)`；重复只更新 `last_seen_at`。
- **base DB 与 sidecar 合并**：同一 `(release, obsid, detector, version)` 以 base DB 为优先（已有 5,893 帧基线），sidecar 只补 base 没有的 epoch；合并后仍按 `(obsid,detector)` 去重，`frame_id` 可为 null（ondemand/ingest 尚未回填）。

## 6. 缓存、TTL、限流

### 6.1 缓存分层

| 缓存 | 键 | TTL | 容量/淘汰 | 一致性 |
|---|---|---|---|---|
| 索引快照 | `snapshot_id` | 不可变；新快照替换 active | 保留 30 天 | 构建完成才 active；旧快照只读 |
| 查询缓存 `/field` | `sha256(normalized request + index_snapshot)` | 正 24 h；负 6 h | LRU 10,000 条 | 快照变更清空；负缓存短 |
| 422 结果 | `(key, ra6, dec6, 0.001)` | 正 7 d；负 6 h | LRU 50,000 | 新周/新版本清负缓存 |
| 头缓存 | `sha256(key)` 或 key | 不可变 | 90 天未引用 GC | 头 sha256 校验；坏头不落盘 |
| 像素/裁剪缓存 | `sha256(release\|version\|obsid\|detector\|ra6\|dec6\|fov\|hdu_set\|pipeline_version)` | 无 TTL（不可变） | **20 GB LRU**；demo 场 pin 7 d | release/version 进键；读时校验 sha256；坏块删除 |
| S3 List | `(release, week, prefix)` | 1 h | 小 | `NextContinuationToken` 翻页 |
| B 星表 | 由 B 负责 | B 决定 | B 决定 | C 只记录 `catalog_release` |

### 6.2 TTL 原则

- **正向**（有数据）可以长：真实文件/版本不可变；像素缓存无 TTL。
- **负向**（无覆盖/无结果）必须短：6 h；新周/新 release 随时可能出现；负缓存不能变成“永久盲区”。
- **错误**不能长缓存：上游错误最多 60 s；`429` 按 `Retry-After`。
- **快照**是事务边界：查询缓存键包含 `index_snapshot`；新快照发布后旧查询缓存自然失效。

### 6.3 缓存一致性规则

1. release/version 必须进所有像素/epoch 缓存键；禁止跨版本复用 NPZ。
2. 写入用“临时文件 + fsync + `os.replace`”；崩溃不留半文件。
3. 读时校验 sha256/JSON 结构；损坏删除并重取，不 500。
4. 内容寻址 blob 只增不减，LRU 只删无引用/未 pin 的缓存；DB 引用与 blob 引用要能对账。
5. 索引快照切换用单行 `active_snapshot` 指针；构建中的快照不可查询。
6. 负缓存不能覆盖“索引不完整”区域；`index_completeness=partial` 时不写负缓存。
7. 任何“无覆盖”结论都必须记录 `method`（footprint/422/tap）和 `index_snapshot`，方便审计/重放。

### 6.4 限流与退避

| 目标 | 并发 | 速率 | 重试 | 熔断 |
|---|---:|---:|---|---|
| IRSA 静态切片 | 4 | 2 req/s | 429/5xx/超时 3 次；0.5/1.5/4.5 s + jitter；404 不重试 | 连续 5 次失败 → 60 s 半开 |
| S3 List/Range | 8 | 10 req/s | 5xx/超时 3 次；429 尊重 `Retry-After` | 连续 10 次 → 60 s |
| TAP | 1 | 1 req/2 s | 1 次；20 s 超时 | 失败 3 次 → 10 min 不用 TAP |
| B catalog | 4 | 5 req/s | 2 次；10 s 超时 | 失败 5 次 → 60 s；标记 deferred |
| 对外 `/field` | — | 60 req/min/IP | — | 429 + `Retry-After: 1` |
| 对外 `/ingest` | 2 个 worker | 5 job/h/token | — | 429；队列深度告警 |

- 单请求预算：本地 2 s；按需发现 90 s（TAP 20 s + S3 60 s + 余量）；像素取数 120 s；ingest 单帧 180 s。
- 全局每日下载预算（建议）：默认 5 GB/日；超过后仅服务缓存，`X-Budget-State: exhausted`。
- 所有外部请求带 `User-Agent: MoveScope-anyfield/1.0`；不携带 secret。
- 断网/超时不能拖死 HTTP 线程：发现/取数在 worker 线程池，主 API 有硬超时。

## 7. 新图增量流程

### 7.1 输入来源

| 来源 | 用途 | MVP |
|---|---|---|
| 官方新周/新 release（S3/IRSA） | 真实新历元 | ✅ |
| 已冻结/本地 FITS fixture | 验收/离线 | ✅ |
| 用户上传 FITS | 研究/演示 | ❌ 后续，默认关闭 |
| 旧 release 重处理（QR3→DR1） | 版本替换 | ✅ 作为新 epoch，不覆盖旧版 |

### 7.2 阶段状态机

```text
queued
  → acquiring        （下载切片/文件，算 sha256）
  → validating       （FITS/HDU/头/坐标/版本）
  → cropping         （HDU 裁剪，只留需要的数组/表）
  → astrometry       （WCS/PSF/FLAGS/质量）
  → reprojecting     （共同网格 + 相对定标）
  → detecting        （批量检测/强制测光）
  → matching         （B 星表；失败可 deferred）
  → committing       （事务发布 epoch + measurement + series revision）
  → committed
任何阶段失败 → failed（staging 清理；不可见）
committed 后 series 重算失败 → committed_with_stale_series（数据保留，重试）
人工回滚 → retracted（软撤回 + series revision +1）
```

### 7.3 各阶段细节

#### 阶段 0：预检 / 幂等

- `Idempotency-Key`（HTTP header）或 `job_id`。
- 文件身份：
  - `content_sha256`：下载后计算；
  - `epoch_id = sha256(release\|version\|obsid\|detector)`；
  - 若 `epoch_id` 已存在且 `content_sha256` 相同 → `replayed=true`，不重复下载/检测；
  - 若 `epoch_id` 已存在但 sha 不同 → **409 `INGEST_CONFLICT`**（同一版本文件被替换，必须人工确认）。
- 先查索引/DB，避免重复下载 4 MB；但“已存在”不能替代文件校验。

#### 阶段 1：获取（acquire）

- 来源为官方：优先静态切片，`size = min(max(fov*1.1, 0.05), 0.5)`；FOV >0.5° 拒绝像素 ingest。
- 来源为 S3 全文件：只在需要整帧/大视场时使用；默认不下载 65 MB。
- 校验：
  - HTTP 200/206；
  - `Content-Type`/首字节 `SIMPLE`；
  - 最大 128 MB；超过拒绝；
  - 计算 sha256；与 `expected_sha256` 不符 → `INGEST_CHECKSUM_MISMATCH`。
- 422 → `INGEST_NO_OVERLAP`，不进入后续阶段。
- 写入临时文件/内存；不写缓存直到验证通过。

#### 阶段 2：FITS 读取（validate）

用现有 `系统/app/core/fitsio.py`（numpy-only）：

- 必需 HDU：`PRIMARY`、`IMAGE`、`FLAGS`、`VARIANCE`；可选 `ZODI`、`EPSF`、`WCS-WAVE`。
- 必需头：`OBSID`、`DETECTOR`、`CRVAL1/2`、`MJD-OBS`、`NAXIS1/2`、`CTYPE1/2`、`BUNIT`。
- 校验：
  - `NAXIS1/2` 在 `[16, 4096]`；
  - `BITPIX` 合法；数据长度足够；无截断；
  - `DETECTOR` 1–6；
  - `MJD` 有限且在合理范围（> 40000）；
  - `OBSID` 的 week/field/repeat 与 key 一致；不一致 → `INGEST_HEADER_MISMATCH`；
  - `RELEASE`/`VERSION` 与请求一致；不一致 → 409。
- 不合格：写 `error_code` + 可读信息；不落 DB 可见行。

#### 阶段 3：HDU 裁剪（crop）

- 以目标 `(ra,dec,fov)` 在 IMAGE WCS 上求 ROI：
  - 目标像素 `(x,y)`；`half = fov*3600/(2*pixel_scale) * 1.1 + 4`；
  - `x0..x1`、`y0..y1` 限制在 `[0,naxis]`；最小 16×16；最大 512×512。
- 只保留：
  - `IMAGE`、`FLAGS`、`VARIANCE`、`ZODI` 的 ROI；
  - `WCS-WAVE` 控制点（全表或 ROI 子集）；
  - `EPSF` 中与 ROI/波长最近的若干行（不要 441×8752 全表）；
  - 裁剪后的 WCS 头（`CRPIX` 平移 `-x0,-y0`，SIP 保留，记录 `ROI_X0/Y0`）。
- 输出：
  - 压缩 NPZ/FITS（建议 float32 图像/方差、int32 flags）；
  - `cutout_sha256`、`roi`、`parent_key`、`release/version`；
  - 目标 `fov ≤ 0.5°` 时 NPZ 约 0.1–2 MB（随 FOV；0.1° 约 100–300 KB），远小于 4 MB 切片。
- 失败：坏像素/全 NaN/ROI 为空 → `INGEST_CROP_EMPTY`；不写。

#### 阶段 4：WCS / PSF / FLAGS（astrometry）

- WCS：
  - 解析 TAN-SIP；检查 `RADESYS=ICRS`、`LONPOLE`、`CD/PC`；
  - 像素→天球→像素往返误差 < 1e-6 px；否则 `INGEST_WCS_INVALID`；
  - 记录 `pixel_scale_arcsec`、`sip_order`、`wcs_sha256`。
- PSF：
  - 从 `EPSF` 选与 ROI 中心最近的 bin；记录 `psf_fwhm_arcsec`、`psf_sha256`；
  - EPSF 缺失 → 用 `app/data/psf_d2.npy` 兜底并标 `PSF_FALLBACK`（质量降级，不伪造）；
  - 记录 `psf_source=epsf|fallback`。
- FLAGS：
  - 用 `photometry.build_mask` 的三级 `bad/soft/ok`；`SOURCE` 位永不屏蔽；
  - `bad_fraction = bad.sum()/pixels`；> 0.5 → `INGEST_TOO_MANY_BAD_PIXELS`；
  - `saturated` 像素比例、`l2dqa` 记录；
  - 生成 `quality` 列表（如 `PSF_FALLBACK`、`HIGH_BAD_FRACTION`、`SATURATED`、`EDGE`）。
- 不做绝对定标；只保留 `MJy/sr` 原始单位。

#### 阶段 5：重投影 / 共同网格（reproject）

- **网格锚点不依赖“第 0 期”**：用请求 `field` 的中心、固定像素尺度、固定 shape，保证后加入的新历元不会改变已有网格。
  - `pixel_scale = median(epoch pixel scales)`，四舍五入到 0.01″；默认 6.15″；
  - `shape = ceil(fov*3600/pixel_scale) + 4`，上限 512；
  - `grid_id = sha256(field_key|wcs|shape|release_group|pipeline_version)`。
- 分组：
  - 按 `(release_group, detector)` 分开；QR3 与 DR1 不共网格；
  - 不同探测器不共网格（波段/PSF 不同）；显示层可另行叠加，但不用于测光。
- 重投影：
  - 用 WCS 把目标网格像素映射到源像素；双线性采样；
  - 图像单位 `MJy/sr` 视为表面亮度，不做通量缩放；
  - 无效像素填 NaN；`valid_fraction` ≥ 0.9，否则拒绝；
  - 记录 `reproject_rms_px`、`valid_fraction`、`grid_id`。
- 相对天体测量：
  - 复用 `pipeline.match_sources`：参考星匹配 + 6 参数仿射 + 鲁棒剔除；
  - 排除目标自身（按预测位置 >6 px）；
  - `n_ref ≥ 3` 且 RMS < 0.35 px 才 `correction_ok`；否则 WCS-only，误差放大并标 `ASTROMETRY_WCS_ONLY`；
  - 仿射改正只用于位置，不用于通量。
- 跨历元：
  - 每个 epoch 独立重投影到同一 grid；不把不同 epoch 的像素先相加；
  - 时间序列拟合在测量层做，不在像素层做。

#### 阶段 6：入库（commit 前的 staging）

- 所有阶段结果先写 `ingest_stage`（`job_id`, `stage`, `input_sha256`, `output_sha256`, `status`, `attempt`, `error`），不写可见业务表。
- 预览/校验接口只能看 staging 的摘要，不能把 staging 当真实历元返回。

#### 阶段 7：检测 / 测量（detect）

- 复用 `pipeline.detect_sources`：
  - 匹配滤波 + 局部极大；阈值 6σ；最多 80 源；
  - PSF/快速质心 + 孔径测光；饱和源用 bloom；
  - 质量标记与 A 的 `sources` 同源。
- 目标测量：
  - 目标位置来自 `targets`（本地 7 个）或 B 的星表匹配；
  - 按 PM/视差传播到该 epoch 的 MJD（由 B/D 提供；C 不自己发明星表历元）；
  - 预测位置附近 `radius = max(4 px, coord_unc/scale + 2 px)` 内选源；无源则强制在预测位置测光；
  - SNR < 3 或无有限通量 → 不写 measurement，记录 `TARGET_NOT_DETECTED`；不伪造 0 通量。
- 盲源：
  - 保留全部检测源（`detections`），供 D 后续盲关联/未知候选；C 不分类。
- 输出：
  - `measurement`：`epoch_id`、`target_key`、`method`、`x/y`（grid）、`ra/dec`、`flux/flux_err`、`snr`、`quality`、`grid_id`、`pipeline_version`；
  - `detection`：可选，供 D；不含 known/unknown 标签。

#### 阶段 8：匹配（match）

- 调 B：
  - `GET /api/v1/catalog/cone?ra=&dec=&radius_deg=&epoch=&catalog=gaia`
  - 或批量 `POST /api/v1/catalog/match`（建议 ≤500 detections/批）。
- 匹配规则由 D/B 定义；C 只记录：
  - `catalog_release`、`catalog_id`、`sep_arcsec`、`match_state`；
  - `match_state=matched|ambiguous|deferred|none`。
- 失败：
  - B 不可用/`CATALOG_UNAVAILABLE` → `deferred`；**绝不**写 `uncatalogued`；
  - B 返回空但 release 正常 → `none`（仅表示“该星表该半径无源”，不是“新天体”）。
- C 不把 `deferred` 当 `none`；D 必须把 `deferred` 归入 `insufficient_data`。

#### 阶段 9：追加 measurement + 重算时间序列

- `series_key = sha256(field_id|target_key|release_group|detector|method)`。
- 一个 ingest 任务对同一 `series_key` 只增加 1 次 `series_revision`（即使新增多个 measurement）；若该 series 没有任何新 measurement，则不增 revision，只记录 `no_new_measurement`。
- 重算：
  - 取该 series 全部 `visible` measurements，按 MJD 排序；
  - 应用 quality 门（bad/saturated/edge/PSF fallback 等）；
  - 调 `pipeline.run_pipeline`/`motion.analyze_track`（复用 app 逻辑）；
  - 写新的 `analysis_run`（`series_revision`、`model`、`mu`、`class`、`quality`、`created_at`）；
  - 旧 revision 保留，不就地覆盖；API 默认返回最新 revision。
- 失败：
  - 数据已 commit → `series_state=stale`，`SERIES_RECOMPUTE_PENDING`；后台重试；不回滚 measurement；
  - 重试 3 次仍失败 → 告警；series 继续指向旧 revision，响应明确 `stale=true`。
- 缓存失效：
  - `result_cache`/app 的 `analysis_id` 缓存按 `series_revision` 失效；
  - 旧分析结果不修改，只标记 `superseded`。

#### 阶段 10：发布 / 通知

- 单事务提交：
  - `ingested_epoch.visible=1`；
  - measurement 可见；
  - `series_revision` 指针切换；
  - `ingest_job.state=committed`；
  - 更新 `active_snapshot` 的增量表（或新快照）。
- 提交后：
  - 清 `/field` 查询缓存中涉及该 `field_key` 的键；
  - 清该 field 的 422 负缓存；
  - 发内部事件（可选 webhook），A/D 可轮询 `dataset_version`；
  - 指标：`ingest_committed_total`、`measurements_added`、`series_revision`。

### 7.4 幂等设计

| 场景 | 行为 |
|---|---|
| 同 `Idempotency-Key` + 同 payload | 返回原 `job_id`，`replayed=true`；不重复下载/检测 |
| 同 `Idempotency-Key` + 不同 payload | 409 `IDEMPOTENCY_CONFLICT` |
| 同 `epoch_id` + 同 `content_sha256` | 200/202 `replayed=true`；行数不变 |
| 同 `epoch_id` + 不同 sha | 409 `INGEST_CONFLICT`；要求新 version 或人工确认 |
| 同 `measurement`（epoch/target/method/pipeline） | `ON CONFLICT DO UPDATE` 仅在 input sha 相同时；否则新 `pipeline_version` |
| 重跑同一 job | 从 `ingest_stage` 断点继续；已成功阶段不重复网络请求 |
| 并发同 epoch | 按 `(release,obsid,detector,version)` 加锁；后到者返回 409/等待 |

### 7.5 回滚设计

| 失败点 | 已发生 | 处理 | 可见性 |
|---|---|---|---|
| acquire/validate/crop/astrometry | 临时文件/staging | 删除 staging/临时文件；job failed | 不可见 |
| reproject/detect/match | staging | 删除 staging；blob 变孤儿 → GC | 不可见 |
| commit 事务内失败 | 部分 SQL 未提交 | SQLite 事务回滚；job failed | 不可见 |
| commit 成功、series 失败 | epoch/measurement 已发布 | 不回滚数据；`series_stale`；重试 | 测量可见，序列标 stale |
| 人工回滚已提交 epoch | 数据已发布 | `retracted_at` 软撤回；`series_revision +1`；审计 | 默认查询过滤；`include_retracted=1` 可见 |
| 版本替换（QR3→DR1） | 旧版已存在 | 新 epoch；旧 `superseded_by`；不删除 | 默认用新版；旧版可审计 |

- **不硬删已提交 measurement**；软撤回保留审计链。
- 回滚必须触发受影响 series 重算，并让 app 的 `analysis_id` 缓存失效。
- 回滚 API 默认仅本地/admin 可用；公网不暴露。

### 7.6 并发与写模型

- SQLite WAL；`busy_timeout=5000`；单写者（ingest worker）。
- 读连接 `PRAGMA query_only=ON`；HTTP 读线程不拿写锁。
- ingest 队列：默认 2 个 worker；同一 `obsid/detector` 串行；不同 field 可并行。
- 大文件下载不入 DB；blob/缓存走文件系统；DB 只存元数据/指针。
- 事务批量：每 100 measurements 提交一次 staging；最终发布一事务。

## 8. 接口设计

### 8.1 通用约定

- Base：`http://127.0.0.1:8798`（C）；JSON UTF-8；时间 MJD（float）优先，`date_obs` UTC ISO。
- `schema_version` 固定 `"1.0"`（与 T1 兼容）；新字段只做加法；破坏性变更走 `/api/v2`。
- `service_version`：`anyfield/1.0.0`；`pipeline_version`：如 `movescope-pipeline/0.2`。
- 每个响应带 `request_id`、`index_snapshot`、`generated_at`。
- 错误体：

```json
{
  "error": {
    "code": "NO_LOCAL_COVERAGE",
    "message": "该天区在本地索引快照 s3-2026W46 中没有真实历元。",
    "retryable": false,
    "request_id": "req_...",
    "details": {
      "coverage": {"state": "none", "fraction": 0.0, "index_completeness": "complete"},
      "sim_allowed": true
    }
  }
}
```

- 不返回 NaN/Infinity；数值统一 JSON null 或有限数。
- 所有列表稳定排序：`(mjd, detector)`；分页 `limit`/`offset` 或 `next_cursor`。

### 8.2 `GET /api/v1/epochs`（兼容扩展）

**用途**：A/B/旧 app 的历元解析；保持现有语义：确认无覆盖时 200 + 空列表 + `coverage.state=none`；不 422；索引不完整/上游失败时 503，不冒充无覆盖。

**实现方式（兼容代理）**：C 的 `/epochs` 先只读现有 DB v1（HTTP `127.0.0.1:8797` 或直接只读 `catalog.sqlite`）取 base epochs，再合并 sidecar 的 ondemand/ingest epochs，按 `(obsid,detector)` 去重后返回。

- base DB 可用 → 正常合并；
- base DB 不可用、sidecar 也无数据 → **503 `DB_UNAVAILABLE`**，不能返回“200 空列表”让 A 以为没有覆盖；
- base DB 不可用、sidecar 有数据 → 200 + `warnings=["DB_UNAVAILABLE"]` + `data_state="sidecar_only"`；
- 索引不完整且无结果 → **503 `INDEX_INCOMPLETE`**；A 应显示“未知/部分”，而不是直接 SIM 成 `NO_LOCAL_COVERAGE`。

> app 迁移路径：设置 `SPHEREX_FIELD_URL=http://127.0.0.1:8798` 时走 C；未设置/ C 不可用时回退现有 DB 8797。C 不改变 DB 端点的现有行为，只提供超集。

**请求**：

```http
GET /api/v1/epochs?ra=269.452077&dec=4.693365&fov=0.1&release=dr1&limit=500

```

参数：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `ra`,`dec` | float | — | 与 `target_id` 二选一；同时给时须在 0.05° 内 |
| `target_id` | string | — | 7 个本地目标 |
| `fov` | float | 0.25 | 0.02–3.0；像素上限另由 `/field` 控制 |
| `release` | string | 全部 | `dr1\|qr3` |
| `detector` | int/CSV | 全部 | 1–6 |
| `mjd_min`,`mjd_max` | float | — | 时间过滤 |
| `limit`,`offset` | int | 500/0 | 分页 |
| `include_superseded` | bool | false | 是否含旧版本 |
| `mode` | `local\|auto` | `local` | `auto` 允许按需发现 |

### 8.6 `GET /api/v1/ingest` / `GET /api/v1/ingest/{job_id}`

- 列表：`?state=&limit=&offset=`；只返回摘要；默认只返回当前/最近 100 条。

- 这些子路径是 v1 的一部分；新增字段只做加法。

## 9. 与 A/B/D 的契约

### 9.1 C → A（点选/分析）

**A 的现状**（`06_ABC任务分发.md`）：`/api/analyze` 响应增加 `sources[]`，字段：

```json
{
  "epoch_id": "...", "x": 72.3, "y": 58.1,
  "ra": 269.452, "dec": 4.693,
  "flux": 12.3, "flux_err": 0.4, "snr": 30.0,
  "saturated": false, "quality": []
}
```

C 对 A 的约束：

1. **A 调 C 的顺序**：
   - 先 `GET /api/v1/field?ra&dec&fov&mode=auto`；
   - 200 → 用 `epochs`/`slice_url` 取数分析；
   - 422 `NO_LOCAL_COVERAGE` → A 显式 `mode=synthetic`/`hybrid`，`fallback_reason=NO_LOCAL_COVERAGE`，UI 显示 SIM badge；
   - 503 `FIELD_UPSTREAM_UNAVAILABLE`/`INDEX_INCOMPLETE` → A 显示“数据源暂不可用”，可回退到旧 DB `/epochs`；无数据时 SIM 但 `fallback_reason` 不得写成 `NO_LOCAL_COVERAGE`。
2. **A 的 `/api/analyze` 响应**必须带：
   - `data.field_id`、`data.dataset_version`、`data.index_snapshot`；
   - `epochs[].epoch_id`（来自 C）；
   - `sources[].epoch_id`（必填，06 已要求）；
   - `provenance`/`fallback_reason` 保持现有语义。
3. **A 不写 C/DB**：A 只读；点选源表是分析产物，不是 C 的 measurement。若未来要把 A 的交互测量回写，另立 `POST /api/v1/ingest/{job}/attach`，本轮不做。
4. **同一检测函数**：C 批量检测复用 `pipeline.detect_sources`，A 的交互检测不另写一套源表；差异只在输入/输出包装，避免“同一张图两个源表”。
5. **FOV 边界**：A 的 UI 可到 3.0°，但 C 的像素路径只到 0.5°；A 对 >0.5° 的 C 真实取数应降级为规划/分块或 SIM，并显示原因。
6. **坐标锁定**：A 点击得到 `ra/dec`，C 不改变用户坐标；0.05° 内命中官方目标只影响 truth/名称，不替换查询中心（现有 `epoch_source` 语义）。

### 9.2 C ↔ B（星表）

**B 的契约**（`06_ABC任务分发.md`）：

```http
GET /api/v1/catalog/cone?ra=&dec=&radius_deg=&epoch=&catalog=gaia
POST /api/v1/catalog/match
```

- 响应带 `release/version`；
- 失败 `CATALOG_UNAVAILABLE`，不能返回“空匹配=新星”；
- 不改 app；独立 `var/star_catalog.sqlite`。

C 对 B 的约束/请求：

1. **C 调 B 只用于匹配，不拥有星表**；C 不导入 Gaia/2MASS/WISE，不复制 `catalog_source`。
2. **C 发送 `epoch` 为 MJD float**（如 `60916.656`）；B 负责 PM/视差传播到该历元，或返回 `pmra/pmdec/parallax` 由 D 传播。C 只存 B 返回的 `catalog_release`/`catalog_id`/`sep_arcsec`，不自行解释 Gaia 参考历元。
3. **批量**：C 需要 `POST /api/v1/catalog/match` 支持 ≤500 detections/批；若 B 只支持单条，C 用并发 4 调用 cone，但必须限流；B 不应被 C 打成 429。
4. **失败语义**：
   - B `CATALOG_UNAVAILABLE`/5xx/超时 → C `match_state=deferred`；
   - B 正常返回 0 源 → `none`（仅表示该星表无源，不是“新天体”）；
   - B 部分失败 → 未返回的条目标 `deferred`，已返回的按结果；
   - C 不得把 `deferred` 当 `none`，D 不得把 `none` 当“新恒星”。
5. **版本**：每个 match 记录 `catalog_release`；C 的 `GET /api/v1/field/{field_id}/measurements` 必须带 `catalog_release`/`match_state`；B 版本升级后旧结果可追溯。
6. **不阻塞 ingest**：B 失败时 ingest 可以提交 measurement（`match_state=deferred`），后续补匹配；C 不因为 B 挂掉丢真实数据。

### 9.3 C ↔ D（识别）

**D 的职责**（`05`/`06`）：已知/未知识别、PM/视差传播、3σ、ambiguity、分类；D 只写设计，代码晚于 A/B。

C 对 D 的契约：

1. **D 只读 C 的测量导出**：
   - `GET /api/v1/field/{field_id}/measurements?format=jsonl|csv`（建议，v1 预留）；
   - 字段：`measurement_id`, `epoch_id`, `field_id`, `target_key`, `mjd`, `ra`, `dec`, `x`, `y`, `flux`, `flux_err`, `snr`, `quality`, `release`, `version`, `release_group`, `detector`, `pipeline_version`, `catalog_release`, `catalog_id`, `match_state`, `superseded_by`;
   - D 也可通过 `GET /api/v1/field` + `GET /api/v1/epochs` 自行取数。
2. **C 不输出标签**：C 不写 `known_star`/`uncatalogued_candidate`/`unknown_*`；这些是 D 的产物。
3. **D 必须处理 `match_state`**：
   - `deferred` → `insufficient_data`，不得判 `uncatalogued`；
   - `ambiguous` → 不得硬指派；
   - `none` + B release 正常 → D 才可进入 `uncatalogued_candidate` 流程（仍需颜色/形态/多历元证据）。
4. **D 不写 C DB**：D 的分类结果存自己的表/服务；若需要回写，另立 D 的 API，避免 C 变成分类库。
5. **版本**：D 的结果必须记录 `dataset_version`/`series_revision`/`pipeline_version`；C 的系列重算后，旧 D 结果标 `superseded`，不静默复用。
6. **验收依赖**：D 的“任意天区”验收必须在 C 的 20 天区/增量通过之后（`05` 的排期）；C 先提供 `measurements` 导出（W6），D 再做分类（W5+ 可先用已知目标）。

### 9.4 契约变更管理

- 所有响应带 `schema_version`；C 的 v1 只加字段/端点，不删/不改语义。

## 10. 验收

### 10.1 环境与 fixture

- 全部测试默认**离线**：本地假 S3/IRSA（参考现有 T4 `tests/test_harvest_headers.py` 的假 S3 模式），fixture FITS 用 `系统/参考 资料/muestras/` 两份真实切片 + 小型合成 FITS。
- 真实网络测试单独标记 `@network`，不进入 CI。
- 临时 DB/缓存放 `/tmp/anyfield-*`；**不写生产 `var/catalog.sqlite`**；测试后清理。
- 记录机器、Python/numpy 版本、缓存冷/热状态。

### 10.2 20 个随机天区（主验收）

**样本生成**：

- 固定 seed `20261115`；在球面上均匀取 20 个点（`u,v ~ U(0,1)`，`lon=2πu`，`lat=asin(2v−1)`）；`fov` 从 `{0.05, 0.1, 0.2}` 固定轮换，避免挑 FOV。
- **不因为“可能没数据”而换点**；20 个全测。
- 另加两组对照（不是替代 20 个随机）：
  - **C+ 10 个已知有覆盖**：7 个预设目标 + 3 个由独立 S3 头确认的场；
  - **C− 10 个已知空白**：由 `week_index` 黄经带 + S3 头/422 独立确认为无覆盖的场。

**独立真值**（不能用 C 自己的索引）：

- 对每个点，独立用 S3 头 + 422（或 TAP，如果可用）确认是否有文件覆盖；
- 记录 `truth_state=covered|blank|unknown`；
- `unknown` 不计入 precision/recall 分母，单独报告。

**指标**：

| 指标 | 目标 |
|---|---|
| 覆盖断言正确率 | 20/20 `state` 与独立真值一致；`false_covered=0`（无数据却 200） |
| 无覆盖 422 正确率 | 真值 blank 的场 100% 422 `NO_LOCAL_COVERAGE`；body 有 `sim_allowed=true` |
| 正向命中 | 真值 covered 的场 ≥90% 返回 ≥1 epoch；≥80% 返回 ≥2 epochs |
| `coverage_level` | 与独立计算的 `n_epochs/baseline` 一致（允许 ±1 期，因 detector 去重口径） |
| 延迟 | 本地 p95 ≤300 ms；冷发现 p95 ≤30 s；p99 ≤60 s（单场） |
| 失败 | 0 个 5xx（有效输入）；0 个 `provenance=synthetic` 出现在真实响应 |
| 可复现 | 同一 `index_snapshot` 下两次请求 `field_id` 相同 |
| 原始结果 | 20 行 CSV 全量保留，不只报通过数 |

**预期分布**：基于 §2.2 粗估，20 个随机点约 8–12 个有 ≥1 期，5–8 个有 ≥2 期；若实际偏离很大，先查索引/检测器，不调整样本。

### 10.3 有/无数据对照

| 用例 | 数量 | 通过标准 |
|---|---:|---|
| C+ 已知有覆盖（7 预设 + 3 独立确认） | 10 | ≥9 返回 ≥1 epoch；≥8 返回 ≥2 epochs；≥5 的 `n_epochs` 与独立值差 ≤1；0 个 422 |
| C− 已知空白 | 10 | 10/10 422 `NO_LOCAL_COVERAGE`；0 个真实 epoch；0 个 200 空列表（`/field`） |
| 边界：只 1 期 | 至少 2 场 | 200，`coverage_level=C0`，UI 标“无法判运动”；不伪造第二期 |
| 边界：部分覆盖 | 至少 2 场 | 200 `state=partial`，`fraction<0.95`，UI 显示比例 |
| 无 release 匹配 | 1 场 | 200 空 + `warnings`；或 422（若完整且无覆盖） |

### 10.4 新历元追加

在临时 DB 上，选一个已有 ≥2 期的场：

1. 记录 baseline：`n_epochs`、`measurements`、`series_revision`、`valid_fraction`。
2. 用真实 fixture（或独立合成的、WCS 正确的新 MJD 文件）ingest：
   - 首次：`state=committed`；`epochs +1`；每个可测目标 `measurements +1`；至少一个目标可测时 `series_revision +1`；`series_stale=false`。
   - 再次同文件：`replayed=true`；`epochs`/`measurements`/`revision` 不变；无重复 measurement。
3. 同 epoch 不同 sha：409 `INGEST_CONFLICT`；无写入。
4. 失败注入（每个阶段至少 1 次）：
   - 下载 500 / 坏 FITS / 缺 HDU / 坏 WCS / ROI 空 / 重投影 valid_fraction<0.9 / 检测异常 / B 超时 / commit 前 kill：
     - job `failed`；可见 `epochs`/`measurements` 计数不变；staging 清理；无半文件。
5. 已提交后 series 失败：
   - `series_stale=true`；epoch/measurement 保留；重试后 revision 增加；不丢数据。
6. 人工回滚：
   - `epoch retracted`；默认查询不见；`series_revision +1`；审计可查；不硬删。

**量化**：`epochs +1`、`measurements +1`、`revision +1`、重复运行 delta=0、失败注入 delta=0。

### 10.5 断网 / 上游故障

- 用环境变量/假 DNS 模拟 `NO_NETWORK=1`；本地索引/缓存/422 仍可用：
  - 有本地历元：200；不访问网络；
  - 无本地历元但快照完整：422；2 s 内返回；
  - 无本地历元、快照不完整：503 `INDEX_INCOMPLETE`；不假装 422；
  - 缓存命中：200；不访问网络；
  - 缓存坏：删除重取失败 → 503；不 500。
- 模拟 IRSA 502/503/429、S3 超时、TAP 502：
  - 重试 ≤3；退避；熔断；`Retry-After` 被尊重；
  - 不产生请求风暴（总请求数 ≤ 候选数 × 3 + 少量）；
  - 有缓存则 200；无缓存则 503/429 明确；
  - app 显示“上游不可用”，不显示“NO_LOCAL_COVERAGE”。
- 100% 无 500；无挂起 >90 s；无“200 空列表”冒充 `/field` 的无覆盖。

### 10.6 延迟 / 限流

| 场景 | 目标 |
|---|---|
| `/api/v1/epochs` 本地（5,893 帧） | p50 ≤30 ms；p95 ≤150 ms；p99 ≤300 ms |

### 10.7 覆盖精度

- 200 个随机点（与 20 个主样本独立），FOV 从 `{0.02,0.05,0.1,0.2,0.5}` 取样。
- 独立真值：S3 头四角 + 422 点确认；对部分覆盖用 25 点采样。
- 指标：
  - **false positive（有覆盖却报无/少报）**：0；
  - **false negative（无覆盖却报有）**：≤2%（4/200）；
  - `fraction` MAE ≤0.05（真值可算的场）；
  - `coverage_level` 一致率 ≥95%；
  - 边界（FOV 角/边）误差 ≤0.02°。

  - app 111 tests 全绿；

## C-MVP 实现状态 / 边界（2026-11-15）

> **历史阶段**：C-MVP 是 P0 之前的只读骨架；当前 P0 见下一节“C-P0 实现状态 / 边界”。
>
> 本节记录 **C-MVP 骨架**，不是完整 C。它只证明“本地只读覆盖查询”这一层可以独立运行；不代表任意天区、按需取数、增量 ingest 已完成。

### 已实现（C-MVP）

- 新增 `系统/anyfield/` 独立只读服务，默认端口 **8798**，只读 `系统/数据库工具/var/catalog.sqlite`。
- 不联网、不写库、不做 ingest、不下载像素、不生成 SIM。
- `GET /api/v1/health`：DB 可读时 200；DB 缺失/不可读时 503 `DB_UNAVAILABLE`。
- `GET /api/v1/field?ra=&dec=&fov=`：
  - 7 个预设目标 0.05° 内命中时，优先用 `target_epochs`，返回 200 + `coverage` + `epochs`；
  - 其余“已知本地覆盖”用 `frames` 中心近似查询（`center_approx`，2.47°）返回 200；
  - 没有本地证据时返回 **503 `INDEX_INCOMPLETE`**，并明确 `strong_assertion=false`、`no_local_coverage=false`；
  - **MVP 不返回 422 `NO_LOCAL_COVERAGE`**，因为还没有完整天空索引，不能做强断言。
- `GET /api/v1/epochs`：同一解析器的 1.0 兼容视图；有本地覆盖 200，未知 503 `INDEX_INCOMPLETE`（不返回空 200 冒充无覆盖）。
- 顶层字段：`schema_version="1.0"`、`service_version="anyfield-mvp/0.1.0"`、`index_snapshot`（DB 元数据派生）、`coverage_mode="center_approx"`。
- `coverage`：`state/mode/method/radius_deg/n_frames/n_epochs/n_observations/n_weeks/releases/detectors/mjd_min/mjd_max/baseline_days/coverage_level/index_completeness/target_id`。
- EpochRef 保持 12 个字段：`obsid/detector/release/week/version/mjd/date_obs/sep_deg/key/slice_url/provenance/frame_id`；`provenance="real"`；`frame_id` 可为 null。
- 测试：`系统/anyfield/tests/`，18 项，使用临时 SQLite fixture，不依赖 8797 服务；覆盖 health、Barnard 200、未知 503、DB 缺失 503、离线解析、只读不修改 DB、`/epochs` 兼容、参数校验。
- 启动：`系统/anyfield/README.md` 与 `系统/anyfield/start.sh`；默认 `http://127.0.0.1:8798`。

### 明确未实现（不要声称完成）

- **真实 WCS 足迹覆盖**：`center_approx` 只是帧中心 2.47° 近似，可能误判边缘/大 FOV；完整 C 的 footprint 算法未实现。
- **完整/按需历元索引**：没有 S3 List/Range、TAP/SIA/DataLink、422 单文件探测、缓存/TTL、限流/熔断。
- **像素取数**：没有 IRSA 静态切片、S3 Range、HDU 裁剪。
- **ingest/增量**：没有 FITS 读取、HDU 裁剪、WCS/PSF/FLAGS、重投影、共同网格、检测/匹配、measurement 追加、series 重算、幂等/回滚。
- **422 `NO_LOCAL_COVERAGE`**：MVP 只返回 503 `INDEX_INCOMPLETE`；强断言留给完整 C。
- **A/B/D 集成**：没有改 app/DB，不提供服务发现/迁移；A/D 仍按原路径。
- **公网/鉴权/写接口**：没有；服务只应绑定本机。

### 结论

- **真实足迹（仅 74 条）**：
  - 从 `frames.header_sha256` 关联的 `blobs(kind='fits-header', zlib)` 解析 `CRVAL/CRPIX/CD|PC+CDELT/NAXIS`；
  - 计算 4 角 TAN 足迹，写 sidecar `anyfield.sqlite.epoch_footprint`；
  - 生产 DB 实测 `headers=74, built=74, failed=0`；
  - **未应用 SIP**：`sip_applied=false`，所以是 `wcs_header` 四角足迹，不是完整 SIP 校正；文档与 API 不把它说成 full footprint。
- **其余 5,819 帧**没有 header：查询明确 `coverage_method=center_approx`（2.47° 帧中心近似），不写 `epoch_footprint`，不得声称真实足迹。
- **每个 epoch** 返回 `coverage_method`/`footprint_method`（`wcs_header`/`center_approx`）；汇总 `coverage.coverage_method`/`footprint_method`、`n_wcs_header`、`n_center_approx`、`index_completeness`。
- 顶层 `coverage_mode="center_approx"` 和 `coverage.method="center_radius_2.47"` 是 C-MVP 遗留兼容字段，**不是** P0 的权威足迹结论；以 `coverage.coverage_method`/`footprint_method` 和 per-epoch 字段为准。
- **200/422/503**：
  - 200：查到本地真实/近似覆盖的 epochs；
  - 422 `NO_LOCAL_COVERAGE`：仅当查询落在 `coverage_region(ra, dec, radius_deg, complete=1)` 且过滤后无 epochs；生产库没有 complete region，因此生产未知天区不会 422；
  - 503 `INDEX_INCOMPLETE`：无证据/索引不完整；`strong_assertion=false`、`no_local_coverage=false`；
  - 503 `DB_UNAVAILABLE`：catalog DB 缺失/不可读；不生成 SIM。
- **metadata-only ingest**：
  - sidecar 表 `ingest_job`、`epoch_extra`、`measurement`；
  - `POST /api/v1/ingest` 接受本地 JSON manifest（epoch 元数据 + footprint + 可选 measurements），不做网络 URL/像素下载；
  - 202 异步；`GET /api/v1/ingest/{job_id}` 状态；`POST /api/v1/ingest/{job_id}/rollback` 软回滚；
  - 幂等键 `epoch_id=sha256(release|version|obsid|detector)`；同 epoch 同内容重复提交 `replayed=true`，不新增 epoch/measurement；
  - 原子发布（epoch_extra + measurement + job committed 同一事务）；失败不留下可见半成品。
- 测试：29 项（原 18 项 C-MVP 用例保持通过 + 新增 footprint/422/ingest 用例）；生产集成用例验证 74 条 header 足迹与 Barnard 的 `wcs_header`。
