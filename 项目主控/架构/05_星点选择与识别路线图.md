# 星点选择与已知/未知识别 · 产品路线图（A/B/C/D）

> 版本：2026-11-15
> 目的：把“任意天区点选一颗星 → 锁定 → 分析 → 判断已知/未知”拆成可排期、可验收的产品阶段。
> 注意：这里的 **A/B/C/D 是产品阶段**，不是 `系统/docs/01_理论设计编排.md` §5.3 的“运动/变光分类阶段 A/B”。

---

## 0. 一句话结论

- **A**：点选图像中的检测源（坐标锁定）。
- **B**：用 Gaia/2MASS/WISE 星表锁定 `source_id`（身份锁定）。
- **C**：任意天区按需取数 + 新历元增量（覆盖与监测）。
- **D**：已知/未知恒星识别与数据比对（身份判定）；**排在 C 之后完整验收**，但 D1 数据层可在 B 后并行启动。

**数据比对任务可以和数据库工具同步，而且应该同步**；但数据库只做“星表数据 + 锥搜索/候选匹配服务”，科学分类留在 MoveScope。不要让 DB 和 app 各自维护一份 Gaia。

## 1. 总排期

以“1 名熟悉仓库的开发者”估算；可并行时按并行算。

| 阶段 | 交付 | 工期 | 依赖 | 建议窗口 | 验收门槛 |
|---|---|---|---|---|---|
| **A** | 点选检测源 → 坐标锁定 → 分析 | 3–5 天 | 现有 `detect_sources` | W0–W1 | 10 个亮源点击分析成功 |
| **B** | Gaia/2MASS 星表 → `source_id` → PM 预测 | 7–10 天（局部场） | A + 星表缓存 | W1–W3 | 已知星 PM 与 Gaia 一致 |
| **C** | 任意天区按需取数 + 新历元增量 | 4–8 周 | B + 全天/按需历元 | W3–W11 | 20 个随机天区；新图可加入 |
| **D** | 已知/未知恒星识别 + 数据比对 | 3–4 周 | B + C；D1 可提前 | W11–W15 | 7 场 + 20 天区；无“新恒星”误报 |

**总计约 11–15 周**（C 取 4 周则 D 可从 W7 开始；C 取 8 周则 W11 开始）。

> D 的“完整任意天区验收”必须在 C 之后；但 **D1（星表数据层）与 B 共用**，可以在 B 完成后立即开始，不必空等 C。

## 2. A/B/C 的边界（先对齐）

### A · 点选检测源

- 暴露 `detect_sources()` 的每期源表；
- 前端画源标记、点击、锁定 RA/Dec；
- 调现有 `/api/analyze`；
- **没有**星表身份，暗源/混合源不可靠；
- 只覆盖本地有历元数据的天区。

### B · 星表身份锁定

- Gaia DR3 主星表；2MASS/WISE 补充红色源；
- `source_id` + PM/parallax + 颜色；
- 用 PM 预测每期位置，forced photometry；
- URL 带 `source_id`；
- 仍只覆盖有 SPHEREx 数据的天区。

### C · 任意天区 + 新历元

- 全天/按需 SPHEREx 历元索引；
- IRSA/S3 取数 + 缓存；
- 新图增量入库、批量检测、更新源测量；
- 公网服务化（鉴权/限流）；
- 没有数据时明确 `NO_LOCAL_COVERAGE`，不伪造。

## 3. D · 已知/未知恒星识别（重点）

### 3.1 D 的目标

给定一个检测源/候选源：

1. 查官方星表（Gaia DR3 / 2MASS / WISE / SIMBAD）；
2. 把星表位置按自行/视差传播到观测 MJD；
3. 用误差椭圆 + 运动矢量做匹配；
4. 输出：
   - `known_star`（含 `source_id`、名称、星表）；
   - `ambiguous`（多个星表源都在匹配半径内）；
   - `uncatalogued_candidate`（无匹配，但形态/颜色像恒星）；
   - `unknown_moving_object` / `unknown_stationary`；
   - `insufficient_data`。
5. **不输出“新恒星/新行星发现”**。

### 3.2 数据比对原理

```text
检测源 (ra, dec, mjd, σ, pm?)
  → 星表锥搜索（Gaia/2MASS/WISE）
  → PM/视差传播到 mjd
  → 3σ 位置匹配
  → 运动矢量一致性（μ_obs vs μ_cat, PA）
  → 颜色/视差/形态补充
  → known / ambiguous / uncatalogued / insufficient
```

匹配公式：

```text
Δra  = (ra_cat(t) − ra_obs) · cos(dec)
Δdec = dec_cat(t) − dec_obs
sep  = sqrt(Δra² + Δdec²)

match if sep < k · sqrt(σ_cat² + σ_obs² + σ_pm²), k≈3
```

**关键**：不能拿 Gaia J2016 坐标直接和 2025–2026 的 SPHEREx 图比；必须先传播自行/视差。高自行星（Barnard）不传播会错几十角秒。

> D 的完整设计见 [07_已知未知识别与数据比对设计.md](07_已知未知识别与数据比对设计.md)；本节只保留路线图层面的摘要。

### 3.3 D 的输出标签

| 标签 | 条件 | 说明 |
|---|---|---|
| `known_star` | 位置 + 运动在 3σ 内匹配 | 返回 `source_id`、名称、星表 |
| `ambiguous` | 多个星表源在半径内 | 6.15″/px 混合；不硬指派 |
| `uncatalogued_candidate` | 无匹配，颜色/PSF 像恒星 | 不是“新恒星”，只是候选 |
| `unknown_moving_object` | 多历元移动，无历元/星表匹配 | 小行星/彗星/TNO/褐矮星都可能 |
| `unknown_stationary` | 无移动，无星表匹配 | 星系/QSO/伪源/混合源 |
| `insufficient_data` | 1 期或 S/N 不足 | 不能判 |

## 4. 数据比对任务如何与数据库工具同步

### 4.1 结论

**可以同步，但采用“DB 做星表服务、App 做科学分类”的单向同步，不做双向复制。**

| 职责 | 数据库工具 | MoveScope |
|---|---|---|
| 星表快照（Gaia/2MASS/WISE） | **拥有**：导入、版本、索引 | 只读查询 |
| 锥搜索 / 候选匹配 | **提供** `/api/v1/catalog/...` | 调用 |
| 检测/测量 | 不做 | **拥有** |
| 已知/未知分类 | 不做（避免 DB 变科学层） | **拥有** |
| `catalog_matches` 持久化 | 可存 | 可异步写 |
| UI/锁定/URL | 不做 | **拥有** |
| 版本/许可/引用 | **拥有** | 展示 |

### 4.2 推荐架构

```text
官方星表（Gaia TAP / IRSA 2MASS/WISE / SIMBAD）
        │  批量导入 / 按场懒加载
        ▼
DB 工具：catalog.sqlite（独立于生产 catalog.sqlite）
  - catalog_release
  - catalog_source
  - catalog_match
  - API: /api/v1/catalog/cone, /api/v1/catalog/match
        │  版本化只读查询
        ▼
MoveScope：检测 → 候选 → 匹配 → 分类 → UI
  - /api/analyze 返回 identification
  - 结果可异步 POST 回 DB 的 catalog_match
```

### 4.3 同步策略

1. **批量导入**（推荐）  
   按 Gaia/2MASS/WISE 数据发布导入本地 `catalog.sqlite`；记录 `catalog_release`（版本、参考历元、导入时间、许可证）。
2. **按场懒加载**  
   第一次查询某天区时，从官方 TAP 取锥形星表，写入本地缓存；后续只读缓存。
3. **在线兜底**  
   本地无缓存时才查 Gaia TAP/IRSA；超时/502 返回 `CATALOG_UNAVAILABLE`，**不能**当成“未匹配/新恒星”。
4. **离线快照**  
   T3 冻结时把演示场的星表缓存一起冻结；断网可复现。
5. **单向同步**  
   星表是只读参考数据；不把 app 的匹配结果反向覆盖星表。`catalog_match` 是分析产物，可异步写。

### 4.4 为什么不把所有 Gaia 塞进 SQLite

- Gaia DR3 约 18 亿源；2MASS 约 4.7 亿；WISE 约 7 亿。全量放进 SQLite 不现实（几十到上百 GB，查询/备份/分发都不合适）。
- 本项目用 **按场缓存 + HEALPix/HTM 空间索引**；7 个预设场很小，任意天区按需取。
- 若要做全天离线，应该用分区文件/列式格式/外部服务，而不是单文件 SQLite。

### 4.5 数据库表建议（独立 `catalog.sqlite`）

```sql
catalog_release(
  id, catalog, version, epoch_ref, imported_at, license, source_url
)

catalog_source(
  id, release_id, catalog_id, ra, dec,
  pmra, pmdec, parallax,
  gmag, bp_rp, jmag, hmag, kmag, w1, w2,
  object_type, healpix,
  PRIMARY KEY(release_id, catalog_id)
)

catalog_match(
  id, analysis_id, detection_id, release_id, catalog_id,
  sep_arcsec, pm_residual, pa_residual,
  ambiguity, confidence, created_at
)
```

索引：`healpix`、`(ra, dec)`、`release_id`；SQLite 可用 R*Tree 做锥搜索辅助。

### 4.6 API 契约

```http
GET /api/v1/catalog/cone?ra=269.45&dec=4.69&radius=0.3&epoch=61210.0&catalog=gaia
→ {
  "release": "gaia-dr3",
  "count": 123,
  "sources": [
    {"catalog_id": "...", "ra": ..., "dec": ..., "pmra": ..., "pmdec": ...,
     "sep_arcsec": ..., "ambiguous": false}
  ]
}
```

```http
POST /api/v1/catalog/match
{
  "detections": [{"ra":..., "dec":..., "mjd":..., "sigma_arcsec":...}],
  "catalogs": ["gaia", "2mass", "wise"]
}
→ {"matches": [...], "release": "...", "unavailable": false}
```

- 每个响应必须带 `release/version`；
- 失败返回 `CATALOG_UNAVAILABLE`，不能返回“空匹配 = 新星”；
- T1 增加契约用例；T6 检查星表版本/表完整性。

## 5. D 的任务拆分与排期

| 子阶段 | 任务 | 主责 | 工期 | 依赖 |
|---|---|---|---|---|
| **D1** | 星表数据层：Gaia/2MASS/WISE 导入、版本、空间索引、缓存 | DB | 3–5 天 | B |
| **D2** | 匹配引擎：PM/视差传播、3σ、运动残差、ambiguity | App + DB 契约 | 4–6 天 | D1 |
| **D3** | 分类/API：known/ambiguous/uncatalogued/insufficient | App | 3–5 天 | D2 |
| **D4** | UI：星表叠加、源卡片、锁定、URL、离线降级 | App | 3–5 天 | D3 |
| **D5** | 验收：7 场 + 20 天区 + 已知高自行星 + 混合/空白场 | T1 | 2–3 天 | D4 |

**D 总计 3–4 周**；D1 在 B 完成后即可开始，与 C 并行。

### 5.1 D 的完成定义

- [ ] 7 个预设场：亮源中 ≥90% 为 `known_star` 或 `ambiguous`，不能静默错配。
- [ ] 已知 Barnard/Eps 的 Gaia `source_id` 正确；PM 与 Gaia 在 3σ 内。
- [ ] 20 个随机天区：有星表则返回匹配；无星表/服务失败明确 `CATALOG_UNAVAILABLE`。
- [ ] 空白场/混合场：输出 `ambiguous` 或 `uncatalogued_candidate`，不输出“新恒星”。
- [ ] 所有结果带 `catalog_release`；离线缓存可复现。
- [ ] 许可/引用：Gaia、2MASS、WISE、SIMBAD 写入 `THIRD_PARTY_NOTICES.md`。

## 6. 风险与边界

| 风险 | 影响 | 缓解 |
|---|---|---|
| Gaia TAP 限流/502 | 查询失败 | 本地缓存 + 明确 `CATALOG_UNAVAILABLE` |
| 6.15″/px 混合 | 一个像素多颗星 | `ambiguous`，不硬指派；用颜色/亮度加权 |
| 星表不完备 | 无匹配被误当新星 | 只输出 `uncatalogued_candidate`；写证伪条件 |
| 自行/视差误差 | 匹配偏 | 传播误差；3σ；高自行星单独校验 |
| SQLite 全量星表过大 | 无法分发 | 按场缓存；全天用外部/分区方案 |
| DB 与 app 契约漂移 | 结果不一致 | T1 契约 + T6 schema 检查 |
| 许可/引用 | 合规风险 | 星表版本/URL/许可证入档 |

---

## 7. 非目标

- 不在 D 阶段做“新行星确认”；D 只做已知/未知**恒星候选**分类。
- 不做全天天体物理分类；不做轨道拟合；不做系外行星凌星搜索。
- 不把“未匹配”写成“新发现”；不把 `uncatalogued_candidate` 写成 `new_star`。
- 不让 DB 工具做科学分类；DB 只做星表服务。
