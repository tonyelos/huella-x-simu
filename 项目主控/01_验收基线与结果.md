## 0. 一句话结论

**三个工具单独看都不弱，合起来还不是一套系统。**

- `app/`（MoveScope）是唯一真正面向赛道交付的产品：多期播放、测量、BIC 分类、公众话术、可证伪条件都成立；Epsilon Indi B 的真实数据结果是全项目最强资产。
- `数据库工具/` 是工程质量最高的一层：SQLite + Blob、27 个测试全过、导出 JSON 与两个项目逐项对账通过；但它目前**不在任何运行时路径上**，是离线物化视图，不是数据层。
- `视图工具/` 是最好看的一层：5,857 帧真实索引、三维地球、天区选择；但它只负责“选天区”，且与 MoveScope 的交接链路（路径、HTTP 方法、坐标精度）三处同时断开。

**官方 4 条硬要求：1 条未达标、1 条达标、2 条部分达标。**

| # | 官方硬要求 | 判定 | 一句话证据 |
|---|---|---|---|
| R1 | 用户输入任意 RA/Dec，看到**该天区**的多期 SPHEREx 图像 | ❌ **未达标** | 无 `target_id` 的自定义坐标走 `generate_epochs()`，返回 `mode=synthetic`；即使输入 Barnard 的精确坐标也一样。数据库有能力返回真实历元，但 app 从不调用。 |
| R2 | 多期图像像“小视频”一样播放 | ✅ **达标** | 4–8 帧、闪烁/叠加/相减/轨迹四种模式、时间轴拖动、空格播放，实测 1–2.6 s 出结果（热缓存）。 |
| R3 | 必须在 5 个指定天体上跑通 | 🟡 **部分达标** | 5/5 HTTP 200；但只有 3/5 用真实数据；只有 **Eps Ind B** 是真实数据上的正确运动检测。Barnard 因饱和判 S，WISE 0855 只有 1 期探测判 U，RW Aur / R Dra 是 HYBRID（模拟时序）。 |
| R4 | 面向公众、非专业用户可用 | 🟡 **部分达标** | 中文公众解释、置信度、证伪条件、REAL/HYBRID/SIM 标识都很好；但仅本机、仅中文、无引导、无移动端适配，研究者模式里的 BIC 面板实际不可见。 |

**最关键的一句话：当前项目没有一条“任意坐标 → 真实 SPHEREx 多期图像”的端到端路径。** 这正好是 R1，也是数据库工具唯一能补、但还没接上的洞。

## 1. 验收方法

1. **官方基线**：以 `参考 资料/01_挑战原文.md` 的 4 条硬要求和 8 条加分项为准，逐条映射到可执行检查。
2. **运行证据**：对 5 个官方目标各跑一次 `POST /api/analyze`（`mode=auto, fov=0.25`），记录 `mode / n_epochs / readiness / class / μ / quality / 耗时`。
3. **反例**：自定义坐标（Barnard 精确坐标、无 `target_id`）、`mode=sample`、非法 FOV。
4. **数据对账**：app JSON ↔ 数据库导出 ↔ 视图工具 `fields.json`，逐项比较行数、字段、坐标、历元。
5. **工程质量**：数据库 27 个测试、`verify --deep`、`check_compat.py`；视图工具静态资源与 JS 语法；app 的文档数字复算。
6. **交叉一致性**：覆盖半径、就绪度、坐标副本、端口、时间基线。

## 2. 五个官方目标的实跑结果

命令（对每个目标）：

```bash
curl -s -X POST http://127.0.0.1:8790/api/analyze \
  -H 'Content-Type: application/json' \
  -d '{"target_id":"<id>","mode":"auto","fov":0.25}'
```

| 目标 | 官方预期 | 模式 | 期数 | 就绪度 | 判定 | μ (mas/yr) | 探测期数 | 真实数据上的结论 |
|---|---|---|---|---|---|---|---|---|
| Barnard's Star | L | REAL | 4 | L2 | **S** | 8033 ± 9899 | 4 | ❌ 未检出显著位移；`SATURATED_SOURCE`，位移 5.35″ 但质心误差 0.4 px |
| Epsilon Indi B | L+O | REAL | 8 | **L3** | **L** | **4707 ± 547** | 8 | ✅ 真实数据正确检出；μ 与 SIMBAD 4.68″/yr 差 0.5% |
| WISE 0855 | L | REAL | 8 | L0 | **U** | — | 1 | ❌ 8 期中仅 1 期达 3σ；坐标歧义 + 目标过暗 |
| RW Aurigae | V | HYBRID | 8 | L2 | **V** | 49 ± 2116 | 8 | 🟡 分类正确，但时序是模拟的；真实只有 1 个时刻 |
| R Draconis | V | HYBRID | 8 | L2 | **V** | 795 ± 2437 | 7 | 🟡 分类正确，但时序是模拟的；真实 3 期集中在 1 天内 |

**判读**：

- **名义分类正确率 3/5**（Eps L、RW V、R Dra V）；但**真实数据上的正确运动检测只有 1/5**（Eps）。
- 这不是算法失败，而是**数据/呈现问题**：Barnard 饱和、WISE 太暗且坐标有 1.6′ 歧义、RW/R Dra 的 SPHEREx 真实历元基线不足。工具的处理是诚实的（显式标记、判 U/S、不硬凑），这一点应作为加分项讲，而不是扣分项。
- 但对评委/观众，**“5 个目标都能跑”不等于“5 个目标都看到了运动”**。演示脚本必须主动解释这一点，否则会被误读为 4 个失败。
- 数据库里有 74 条候选历元、Eps 10 期/361 天、Barnard 4 期/204 天；数据库不是没数据，是 app 没用到它。

### 2.1 自定义坐标（R1 的关键证据）

```bash
curl -s -X POST http://127.0.0.1:8790/api/analyze \
  -H 'Content-Type: application/json' \
  -d '{"ra":269.452077,"dec":4.693365,"fov":0.25}'
```

返回：

```json
{
  "data": {
    "mode": "synthetic",
    "n_epochs": 8,
    "provenance": ["synthetic"],
    "note": "自定义坐标：使用模拟时序演示识别流程"
  }
}
```

即使坐标**精确等于 Barnard's Star**、且数据库里就有 4 期真实历元，app 仍然生成模拟时序。原因在 `app/server.py::run_analysis` 的 custom 分支：只调用 `generate_epochs()`，从不查 `epoch_catalog.json`、IRSA 或数据库。

> 这不是“数据不够”，是“路径不存在”。

### 2.2 其他错误路径

| 场景 | 结果 | 影响 |
|---|---|---|
| `mode=sample`（UI 提供的“离线样本”） | **HTTP 500** `cannot convert float NaN to integer`，0.02 s | 用户点一下 UI 就报错；默认 Barnard 必现 |
| `fov=-0.2` | **HTTP 500** `high - low < 0` | 参数校验缺失 |
| `fov=0` | 静默使用 24 px（约 0.041°） | 与文档最小 0.02° 不符 |
| `target_id=barnard` + `ra=10&dec=10` | 仍返回 Barnard | 覆盖参数被静默丢弃，嵌入方会拿到错误结果 |
| IRSA 全部失败（模拟断网） | 8 期全部 `provenance=synthetic`，但 `mode=hybrid`，note 写“基线 361 天不足以判定” | **失败原因被误报**；见 §5.2 |

## 4. 三工具贴合度

“贴合”不只看功能多少，按 5 条判：

1. 是否直接服务官方硬要求；
2. 是否在验收/演示路径上（评委会不会碰到）；
3. 是否与其余工具共享数据契约；
4. 是否有明确 owner 和可复现构建；
5. 是否与别的工具职责重叠。

| 工具 | 实际角色 | 1 服务要求 | 2 在路径上 | 3 共享契约 | 4 可复现 | 5 无重叠 | 贴合度 |
|---|---|---|---|---|---|---|---|
| `app/` MoveScope | 产品主体 | ✅ R1–R4 都碰 | ✅ 唯一入口 | ⚠️ 只读本地 JSON | ✅ 无构建、文档全 | ✅ | **4/5** |
| `数据库工具/` | 数据层/目录 | ✅ 能补 R1 | ❌ 运行时无人调用 | ⚠️ 导出通过、HTTP 不兼容 | ✅ 27 测试/完整性通过 | ✅ | **3/5**（战略 4.5，现状 1.5） |
| `视图工具/` | 天区上下文 | ⚠️ 仅辅助选天区 | ❌ 交接断开 | ❌ 复制 targets/fields | ⚠️ fields 已无法重建 | ⚠️ 与 app 目标/历元重复 | **1.5/5** |
| **系统整体** | — | — | — | ❌ | ❌ 无 git | — | **2.5/5** |

**用一句话定位：**

- `app/`：**产品层**，保留并加强。
- `数据库工具/`：**数据层**，保留并接线；不要让它变成第二个产品。
- `视图工具/`：**上下文层**，降级为可选伴侣；修不好就从验收路径移除。

### 4.1 三者之间的真实关系

```
         参考 资料（事实/坐标/访问笔记）
                    │
      ┌─────────────┼──────────────┐
      ▼             ▼              ▼
   app/  ◄────── 数据库工具 ─────► 视图工具
   (产品)        (离线导出)         (上下文)
      │             ▲                │
      │             │ 一次性导入      │
      └─────────────┴────────────────┘
              没有运行时调用
```

- 数据库**从** app/视图工具导入数据；
- 数据库**能导出**成两者兼容的 JSON；
- app **从不**调用数据库；
- 视图工具 **从不**调用数据库，只读自己的 `fields.json`；
- app 与视图工具之间只有一条**已断**的 `../app/index.html` 链接。

所以它不是“三层架构”，而是**三个各自能跑的工具 + 一个离线数据转换器**。

文档层面也印证了这一点：`docs/01_理论设计编排.md` 只描述 MoveScope；数据库的 README/INTEGRATION 是后补的；视图 README 仍写 “docs P3 / HUELLA_X”。**没有一份三工具共同的架构文档**——这正是它们各自演化的原因。本目录的 [02_架构设计与集成契约.md](02_架构设计与集成契约.md) 是补上的第一版系统级架构。

## 5. 缺陷登记（按严重度）

## 6. 交叉一致性矩阵

| 量 | app | 数据库工具 | 视图工具 | 结论 |
|---|---|---|---|---|
| 目标数 | 7（5 官方） | 7 | 7 | 数量一致，字段不一致 |
| 历元 | 74 条（app JSON） | 74 条 `target_epochs` + 5,857 `frames` | 无 | 两套“历元”语义 |
| 曝光/帧 | 5,544 曝光 → 5,857 帧 | 5,544 obs / 5,857 frames | 5,857 行，但 README 写“5,857 次曝光” | 视图口径错 313 |
| 时间范围 | 2025-04 至 2026-10 | MJD 60793.5–61316.5 | 同左 | 数据止于 2026-10-03 |
| 覆盖半径 | `find_epochs` 场 7.5°、探测器 1.9° | 1.745° | 1.745° | 三套阈值 |
| 就绪度 | 检测期数 + 基线 ≥0.6 yr | 曝光期数 + 基线 ≥180 d | 无 | 语义+阈值都不同 |
| targets 字段 | 含 `coord_unc_arcsec` | 导出已保留（v4） | **缺** | 视图副本漂移 |
| 深链 | `?target=&ra=&dec=&fov=` | `/api/epochs?ra=&dec=` | 只读 `#hash` | 三套 URL 语法 |
| 端口 | 默认 8765 / 文档 8790 | 8797 | 扫 8790–8829 | 会撞 |

**四个必须统一的常量/语义：**

1. **覆盖半径**：统一用半对角线 2.47°（或按探测器 footprint + 422 覆盖探测），不要再用 1.745° 当默认；`1.9°` 只保留为“目标确认”阈值并注明。
2. **就绪度**：`coverage_level`（观测机会）≠ `analysis_readiness`（检测质量）；UI 只显示后者，DB 只承诺前者。
3. **历元 DTO**：`obsid / detector / release / week / version / mjd / date_obs / sep_deg / key / slice_url` 十字段，两个 API 完全一致。
4. **日期**：`date_obs` 必须非空；缺失时由 MJD 反推 UTC，不允许把 null 传给前端。

## 7. 验收判定（提交门槛）

以“能不能提交”为标准，而不是“代码写得好不好”：

| 门槛 | 当前 | 说明 |
|---|---|---|
| G1 任意坐标至少对“本地已覆盖天区”返回真实多期图像 | ❌ | 现在全 synthetic |
| G2 5 个官方目标全部可跑，且至少 3/5 使用真实数据 | 🟡 | 3/5 real，但只有 1/5 real+correct |
| G3 UI 暴露的模式无 500（sample、非法 FOV） | ❌ | sample 500、FOV 负数 500 |
| G4 关键面板可见（BIC、历元列表） | ❌ | 父级 hidden |
| G5 断网可完成 5 目标演示 | ✅（已实测） | 阻断 `urllib` 后跑完整管线：5/5 成功，结果与在线一致；缓存 55 个 NPZ / 15 个 pointing 区域。缺的是清单、sha256 校验与可移植快照，不是“跑不起来” |
| G6 一条命令启动 / 一条命令验收 | ❌ | 三套启动方式、无验收脚本 |
| G7 有可回滚的版本基线 | ❌ | 无 git |

**结论：当前状态未达提交门槛。** 但 G1/G3/G4/G6 都是 1–2 天内可修的“接线/校验/可见性”问题，不是重写。
